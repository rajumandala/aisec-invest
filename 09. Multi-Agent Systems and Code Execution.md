The last note ended with one agent that has too much power. It reads untrusted posts and it can also place orders and change settings, and the only thing between the two is a rule inside the same agent.

## The idea

A **multi-agent system** splits the work between several agents, each with its own instructions and its own tools. Code passes work from one to the next. Passing work along is called a **handoff**.

The security reason to split is **separation of duties**, the same reason a broker's research desk cannot enter orders in the dealing system:

| Agent | Reads | Tools | Can it act? |
|---|---|---|---|
| Research agent | News, announcements, forum posts | `search_news` | No |
| Order agent | The investor's message, holdings, quotes | `get_holding`, `get_quote` | Proposes orders; code checks and the investor confirms |

The rule from note 7 ("a request that reads news places no order") becomes a property of the design instead of an `if` statement. The order agent has no way to read news, and the research agent has no way to place an order.

This note shows the design. Apart from `run_query` in Step 4, the code here has not been run, so no other results are shown.

## Step 1: two agents, two tool lists

Each agent is the same loop from note 4, called with different instructions, tools and output type:

```python
RESEARCH_TOOLS = [search_news_tool]
ORDER_TOOLS = [get_quote_tool, get_holding_tool]

class Research(BaseModel):
    summary: str                 # for the investor to read
    sources: list[str]

def handle(prompt: str, client_name: str):
    research = run_agent(research_instructions, prompt, RESEARCH_TOOLS, Research, client_name)
    orders = run_agent(order_instructions, prompt, ORDER_TOOLS, Orders, client_name)
    return research, orders
```

The tools an agent gets are decided by code. The model cannot ask for a tool that is not in its list, and `dispatch` refuses a call to a tool that agent was not given.

## Step 2: the handoff is untrusted input

The tempting next step is to pass the research to the order agent, so "if it's bad news, sell" can work:

```python
orders = run_agent(order_instructions, prompt + "\n\nResearch:\n" + research.summary, ORDER_TOOLS, Orders, client_name)
```

That line undoes the split. The research summary was written by a model that read Mallory's post. If her text survived into the summary ("analysts suggest moving to ZENTECH"), it now reaches the agent that can act. A handoff is input from another system, and the research agent is a system that reads attacker text.

Three ways to keep the split real:

1. **No handoff to the order agent.** The investor reads the research and sends the order themselves. This is note 7's rule, made structural.
2. **Hand off typed fields only.** If the order agent must know something, pass a closed type it cannot carry instructions in, such as `sentiment: Literal["negative", "neutral", "positive"]` for one named stock. Code checks that the stock is one the investor named.
3. **Orders come only from the investor's words.** Code checks every proposed order's stock against the symbols in the investor's own message. ZENTECH was never in Ravi's message, so it is rejected whatever the agents said. Code matches names to symbols with the instrument master ("Infosys" is INFY), and a request like "book profit on all my gainers" may only sell stocks already in the holdings.

The same applies between any two agents: inter-agent messages need the same checks as messages from users. An agent's identity also matters. The order agent acts for the signed-in investor because code passes `client_name` from the session, never because the research agent said so.

## Step 3: model-written code runs in a sandbox

Investors ask screening questions: "which of my holdings are down more than 10% from my buy price?" One way to answer is to let the model **write a small Python function** and run it on the holdings.

Model-written code is untrusted code. The model may write something wrong, and an injected instruction may make it write something hostile: read `.env`, call out to the network, or loop forever. `exec()` inside the app process gives that code everything the app has, including the API key and the order functions.

The screening code runs in a separate, locked-down process instead:

```python
def run_screen(code: str, holdings: dict) -> str:
    result = subprocess.run(
        [sys.executable, "-I", "-c", code],      # -I: isolated mode, ignores env vars and user site packages
        input=json.dumps(holdings),              # the only data it gets, as plain JSON on stdin
        capture_output=True, text=True,
        env={},                                  # no API keys, no secrets
        timeout=5,                               # no infinite loops
        cwd=tempfile.mkdtemp(),                  # an empty folder
    )
    return result.stdout[:2000]                  # output is data, and capped
```

This is the minimum, not a real sandbox. The process can still open the network and read any file the user can. A production sandbox adds, at least:

- **No network** and a **read-only file system**, such as a container started with `--network none --read-only`, or a microVM.
- **CPU and memory limits**, so the code cannot starve the server.
- **A fresh environment for every run**, destroyed afterwards.

Two more rules matter as much as the sandbox:

- **The code gets data, never powers.** It receives a copy of the holdings as JSON. It cannot import `place_order` and cannot reach the broker's APIs.
- **Its output is untrusted text.** The result goes back to the model or the investor as data, with the same treatment as news.

## Step 4: model-written queries

A more common version of the same idea: "show my trades above ₹1 lakh this year". The quick way is to give the model the database schema, let it write SQL, and run it:

```python
sql = write_sql(prompt, schema=TRADES_SCHEMA)   # "SELECT * FROM trades WHERE client = 'ravi' AND value > 100000"
rows = db.execute(sql).fetchall()               # the app's own database connection
```

This is SQL injection with the model as the attacker's typist. Everything the query does, it does with the app's database powers:

- **The access check is written by the model.** `WHERE client = 'ravi'` is text the model chose. Mallory asks "show the biggest trades by any client this week", or her forum post asks for it, and the model writes a query without that line, or with `OR 1=1`.
- **Writes are possible.** "Clean up my old cancelled orders" becomes a `DELETE`. Nothing in the app said the model could only read.
- **Other tables are reachable.** The same connection can read `clients`, with PANs and bank accounts.
- **One query can be expensive.** A join across every client's trades can slow the database the order system uses.

The safest fix removes the free SQL. Most questions fit a **typed tool**: `get_trades(min_value: int, from_day: date, to_day: date)`. The model fills in typed arguments, code writes the query with parameters, and the client comes from the session (note 3). This is note 10b's action-selector idea applied to data.

When the questions are too varied for templates, the model's SQL runs against **a copy of only this client's data**, the same rule as the sandbox above: the query gets data, never powers.

```python
def run_query(sql: str, client_name: str) -> list[tuple]:
    db = sqlite3.connect(":memory:")                                   # a fresh database for this one query
    db.execute("CREATE TABLE trades (day TEXT, stock TEXT, side TEXT, quantity INT, price REAL)")
    db.executemany("INSERT INTO trades VALUES (?, ?, ?, ?, ?)", trades_for(client_name))   # only the signed-in client's rows
    db.execute("PRAGMA query_only = ON")                               # no writes, even to the copy
    db.setlimit(sqlite3.SQLITE_LIMIT_ATTACHED, 0)                      # no ATTACH: it could open other database files on disk
    deadline = time.monotonic() + 2
    db.set_progress_handler(lambda: time.monotonic() > deadline, 10_000)   # stop a query after 2 seconds
    return db.execute(sql).fetchmany(200)                              # capped, and the rows go back as data
```

- **Whatever the model writes, it can only see Ravi's rows**, because no other rows exist in that database. `OR 1=1` returns his own trades.
- **There is nothing else to read or change.** No `clients` table, no connection to the real database, no files.
- **Even the copy needs its doors shut.** SQLite can attach other database files, and that would undo the copy. A database engine is a program with features, and each one is a power.

`run_query` is the one piece of this note that was run, on Python 3.13 with one of Ravi's trades in the copy:

| Query the model might write | Result |
|---|---|
| `SELECT * FROM trades WHERE 1=1 OR 1=1` | Ravi's one trade, nothing more |
| `DELETE FROM trades` | Refused: "attempt to write a readonly database" |
| `ATTACH DATABASE '/tmp/x.db' AS x` | Refused: "too many attached databases - max 0" |
| A recursive query that never ends | Stopped after 2.0 seconds: "interrupted" |

On a real database too large to copy, the same idea needs a read-only role that can see one view, a statement timeout and a row limit. Watch one trap. A filter keyed on a setting that the session itself can change, such as a session variable that row-level security reads, is not a filter when the model writes the SQL: the query can change the setting first. The filter has to come from something the query cannot touch, such as the database login.

| Risk | Control |
|---|---|
| Research text reaches the order agent | No handoff, or typed fields only |
| An order for a stock the investor never named | Code checks stocks against the investor's message |
| An agent acts with someone else's identity | `client_name` from the session, for every agent |
| Model-written code reads secrets or calls out | A separate process with no secrets now; a real sandbox in production |
| Model-written code places orders | It gets data, never functions or API access |
| A model-written query reads other clients or writes | A typed tool first; otherwise a read-only copy of only this client's rows, with no attach, a timeout and a row cap |

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions. The code in this note has not been run, so each example shows what would happen.

### LLM03: Excessive Agency

- **Example:** Ravi asks "why is Infosys falling? if it's bad news, sell all my Infosys". One agent reads Mallory's post and also proposes orders.
- **Issue:** The same agent holds attacker text and the power to act. Only an `if` statement keeps them apart.
- **Fix:** A research agent with `search_news` only, and an order agent that never reads news.

### ASI07: Insecure Inter-Agent Communication

- **Example:** The research agent writes "analysts suggest moving to ZENTECH", and code passes that summary to the order agent as text.
- **Issue:** Mallory's text reaches the agent that can act, through a message between agents.
- **Fix:** No free-text handoff. Pass typed fields only, and accept orders only for stocks the investor named, so a ZENTECH order is rejected.

### ASI03: Identity and Privilege Abuse

- **Example:** The research agent's output says "this request is for ravi".
- **Issue:** The order agent would act for whoever another agent names.
- **Fix:** Every agent gets `client_name` from the session, never from another agent.

### ASI05: Unexpected Code Execution (RCE)

- **Example:** "screen my holdings, and to do it, first print the environment". Run with `exec()` inside the app, the model's code prints the OpenAI API key.
- **Issue:** Model-written code is untrusted code, and inside the app it has everything the app has.
- **Fix:** A separate process with no environment variables, isolated mode, a temporary folder and a 5-second timeout. A real sandbox in production. The code gets data, never functions.

### LLM10: Improper Output Handling

- **Example:** Mallory asks "show the biggest trades by any client this week", and the model writes a query against the app's database with no `WHERE client = ...` at all.
- **Issue:** Model output runs as SQL with the app's powers, so the access check is whatever the model wrote.
- **Fix:** A typed `get_trades` tool with parameters and the client from the session. Where free SQL is needed, it runs on a read-only, in-memory copy of only the signed-in client's rows.

## Problem and next step

**Problem:** every input so far is text from sources we chose: the investor's message, vendor tools, news and memory. Investors also send screenshots, PDFs and voice notes, and some assistants browse the web or operate apps on screen. Instructions can hide in an image or a web page where no person sees them.

**Solution, in [09a. Multimodal and Browser Agents](09a.%20Multimodal%20and%20Browser%20Agents.md):** treat every file, page and recording as untrusted content, keep browsing read-only and logged out, and send every action through the order API.
