The last note ended with a system that is reviewed but not yet allowed. A broker is regulated, and orders produced by software are a regulated activity. Who is accountable when the assistant gets something wrong, and what evidence must the broker keep?

## The idea

**Governance** is how an organisation shows that a system is used responsibly: who owns it, which rules apply, how changes are approved, and what evidence proves the controls work. Security asks "can it be attacked?". Governance asks "can we show a regulator, an auditor or a client what it did, and why?".

The short answer for a broker in India: **the broker is accountable**. Not the model provider, not the framework, not the vendor.

This note is a map for engineers, not legal advice. The rules below are summarised as of October 2026, and some were still proposals at that time. The broker's compliance team decides how they apply.

## Step 1: the rules that touch the assistant

**SEBI's guidelines on AI/ML.** In June 2025 SEBI published a consultation paper on responsible use of AI and ML in the securities market. Its main points, as proposed:

- The regulated entity stays **accountable** for AI tools in its operations, whether built in-house or bought from a vendor.
- **Human oversight**, with people inside the firm who understand the models.
- Testing and monitoring of models, and fallback plans, including a **kill switch**.
- **Data controls**, and agreements with third-party providers.
- **Disclosure** to clients when AI is used in services that affect them.

In August 2026 SEBI said final guidelines along these lines were coming. Check for the final version before relying on any detail.

**Retail algorithmic trading.** SEBI's February 2025 circular on safer retail participation in algorithmic trading puts the broker in the position of **principal** for orders that come through its APIs. Algorithms above a set orders-per-second threshold must be registered with the exchange and tag orders with an **algo ID**. Whether an assistant that proposes an order and waits for the investor's exact "yes" counts as an algo is a question for compliance and the exchange. The design in these notes makes it easier to answer: the investor's confirmation is what triggers every order, and it is logged.

**Investment advice.** Explaining why a stock fell is different from telling someone to buy one. Advice for a fee needs SEBI registration as an investment adviser. An assistant that says "smart money is moving to ZENTECH" is giving advice, and possibly someone else's pump. That is one more reason our instructions say to answer only from what search returns, naming the source, and to leave the decision with the investor.

**Personal data.** Holdings, orders and chat history are personal data under the Digital Personal Data Protection Act, 2023. Sending them to a model provider, a vendor or a tracing service is processing that needs a purpose, a contract and a retention period. The data-flow diagram from note 12 is the starting point for that list.

**Cyber security.** SEBI's cyber security and cyber resilience framework for regulated entities already covers logging, incident response, third-party risk and audits. The assistant adds new systems to its scope: the model provider, the vendor's MCP server, the vector index, the memory store and the saved sessions.

## Step 2: the evidence

If a client says "I never placed that order", the broker must show exactly what happened. Every request writes one audit record:

```python
def audit(event: str, **fields):
    record = {"time": datetime.now(timezone.utc).isoformat(), "event": event,
              "request_id": REQUEST_ID, "client_name": SESSION.client_name, **fields}
    AUDIT_LOG.write(json.dumps(record) + "\n")         # append-only store, not the app's own log file

audit("model_call", model=MODEL, instructions_version=INSTRUCTIONS_VERSION, steps=step)
audit("tool_call", tool=call.name, arguments=call.arguments)
audit("retrieved", sources=[doc["source"] + " " + doc["date"] for doc in results])
audit("check_order", order=order.model_dump(), problems=problems)
audit("confirmation", question=question, answer=answer)
audit("placed", order=order.model_dump(), exchange_order_id=order_id)
```

What the record must make possible:

| Question | Answered by |
|---|---|
| Who asked, and what? | `client_name` from the session, and the prompt |
| Which model and which instructions? | Model name and version, `instructions_version` |
| What did it read? | Tool calls and retrieved sources |
| What did it propose, and what did code say? | `check_order` results, including rejections |
| What exactly did the investor approve? | The confirmation question and the answer, with the time |
| What reached the exchange? | The placed order and the exchange's order ID |

The audit log is sensitive data and evidence at the same time:

- **Append-only**, so nobody can quietly edit history, not even the app.
- **Access-controlled**, because it holds holdings and orders for every client.
- **Kept for the period the rules require**, then deleted.

## Step 3: change control

Most real failures come from a change: a new model, a new prompt, a vendor update, a framework upgrade. Each one goes through the same gate:

1. **Pin everything that changes behaviour:** the model version, the instructions version, vendor tool fingerprints and framework versions.
2. **Run the eval suite.** Security cases must pass on every run (note 5). Keep the report with the release.
3. **Record who approved the change,** especially new vendor pins and new tools.
4. **Roll out with the kill switch ready** and the monitoring from note 12 watching.

## Who owns what

| Area | Owner |
|---|---|
| The assistant as a whole, and its risks | A named business owner at the broker |
| `check_order` and the RMS limits | Risk management |
| Instructions, tools and evals | The engineering team, with security review |
| Vendor review and pins | Security and procurement |
| Data flows, consent and retention | The data protection officer |
| Rules, disclosures and the algo question | Compliance |

## End of the course

The assistant began as one model call that invented prices. Every note after that kept one rule: **the model proposes, code decides**. The model reads and writes text. Code checks identity, limits, prices, sources, memory, handoffs and approvals, and a human confirms the exact order. Each attack that got through became a permanent test.

The same pattern carries over to any agent that acts in the real world: payments, healthcare, IT operations. Put the controls in code, treat every piece of text the model reads as coming from an attacker, and keep the evidence.
