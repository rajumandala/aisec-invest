The last note ended with three things that all "run in a sandbox": the screening code from note 9, the research browser, and the computer-use agent. Note 9 said its own version was "the minimum, not a real sandbox". This note is about what a real one is, and how code gets out of it.

## The idea

A **sandbox** is a boundary around code you do not trust. Code inside can reach only what the boundary lets through. Three questions decide whether it holds:

1. **How strong is the wall?** What does the code have to break to get out?
2. **What goes through the wall on purpose?** The network, files, secrets, and the result.
3. **What happens to what comes out?** Something outside the sandbox reads its output. If that something runs it, the wall did not matter.

Most real escapes from AI sandboxes in 2025 and 2026 used questions 2 and 3, not question 1. Nobody broke the wall. They walked through a door someone had left open.

In AppSec terms, a sandbox is a trust boundary drawn around a process instead of around a network or a user. The model is the attacker's typist, as in note 9's SQL example: whatever Mallory's forum post makes it write, the sandbox runs.

A few terms first. The **kernel** is the core of the operating system: it controls memory, files, the network and every other process. Programs ask the kernel for things through **system calls** ("open this file", "send this packet"). A **hypervisor** runs whole virtual machines, each with its own kernel, on one physical machine.

## Step 1: what a container shares

Note 9 suggested a container started with `--network none --read-only`. A **container** is an ordinary process on the host with two kinds of restriction: **namespaces** give it its own view of files, processes and the network, and **cgroups** limit the CPU and memory it can use. It is not a separate machine. Every container on a host shares the host's one kernel.

That is why a container is a good wall for code you mostly trust, and a thin one for code an attacker may have written:

- **A bug in the kernel or the container runtime is an escape.** In 2024, **Leaky Vessels** (CVE-2024-21626) showed that `runc`, the program that starts most containers, leaked a handle to a host directory. A container could start with its working directory on the host's file system, and read or write host files from there. [M6 in Part M](https://github.com/rajumandala/ai-supplychain/blob/main/notes/M6.%20Running%20Models%20on%20Your%20Own%20Servers.md) showed the same class of bug in the software that gives containers a GPU.
- **Some settings remove the wall entirely.** `--privileged` gives the container nearly every power the host has. Mounting the Docker socket (`/var/run/docker.sock`) lets the container start new containers with any settings, which is root on the host. Running as root inside the container makes every kernel bug worth more.

## Step 2: three strengths of wall

| Sandbox | How it works | What an escape needs | Cost |
|---|---|---|---|
| **Container** | A host process with namespaces and cgroups. System calls go straight to the host kernel | One bug in the host kernel or the runtime | Almost none |
| **gVisor** | A kernel written in Go that runs as an ordinary process. It answers the code's system calls itself, and makes only a small set of its own calls to the host | A bug in gVisor and then one in the smaller part of the host kernel it uses | Some slowdown on file and network-heavy work; a few programs do not run |
| **MicroVM**, such as Firecracker | A tiny virtual machine with its own kernel, run by a hypervisor | A bug in the hypervisor | A little memory per VM; Firecracker starts in about 125 ms |

These are in real use for exactly this job. gVisor's list of users includes Anthropic, for code execution in claude.ai, and OpenAI, for some higher-risk tasks such as code execution. Firecracker runs AWS Lambda and several sandbox services for AI agents.

For the screening code, the model wrote it after reading text Mallory may control, and it runs on the broker's servers next to other clients' work. So it gets gVisor or a microVM, not a plain container. The container settings still matter inside the stronger wall (an example):

```bash
docker run --rm -i \
  --runtime=runsc \
  --network none \
  --read-only --tmpfs /tmp:size=16m \
  --user 65534:65534 \
  --cap-drop ALL --security-opt no-new-privileges \
  --memory 256m --cpus 0.5 --pids-limit 64 \
  screen-runner@sha256:<reviewed digest> \
  python -I /run.py < holdings.json
```

- `--runtime=runsc` runs the container under gVisor, so its system calls go to gVisor, not the host kernel.
- `--network none` gives it no network device at all, not even DNS.
- `--read-only` with a small `--tmpfs` leaves nothing writable except a 16 MB scratch area.
- `--user 65534:65534` runs as "nobody", never root. `--cap-drop ALL` and `no-new-privileges` remove the extra powers a process can otherwise hold or gain.
- The limits on memory, CPU and processes are Step 5's.

`run.py` is fixed code in the reviewed image that reads the model's function and the holdings from standard input. No package is installed at run time: the image already has the few libraries screening needs, so the sandbox never needs the internet.

## Step 3: the network is the usual way out

Code that cannot leave can still send data out. Data that leaves is the leak, whether or not the code escaped.

**DNS is network too.** **DNS** is the system that turns a name like `example.com` into an address. Asking for `ravi-holdings-INFY-120.mallory.example` sends that whole name to whoever runs `mallory.example`. Data can leave a piece at a time, inside the names, and replies can carry commands back. In March 2026, the security company BeyondTrust reported on Amazon Bedrock AgentCore's Code Interpreter, an AWS service that runs code written by AI agents. Its "sandbox" network mode still answered DNS queries. Their proof of concept started with a malicious CSV file, whose text steered the model into writing code that set up a two-way channel over DNS. AWS said the behaviour was intended, updated its documentation, and pointed customers to a mode with full network isolation and a DNS firewall.

The lessons apply to any sandbox the broker runs or buys:

- **"No network" has to mean no DNS.** `--network none` gives the container no network device. A vendor's "sandbox mode" may not. Read what it blocks, and test it.
- **Test from inside.** Run a lookup of a name in a domain the team controls, and check that the domain's server never sees it. Add that as a security case in note 05's evals, so a later change cannot quietly open it.
- **If the code truly needs one service, give it a proxy.** The sandbox reaches one proxy, and the proxy allows one destination and logs every request. It never gets a route to the internet.

## Step 4: what goes in, and what comes out

**In:** only the data for this task. Note 9's rule holds: the code gets data, never powers. That means a copy of this client's holdings, no environment variables, no keys, no mounted folders from the host, and no route to the cloud metadata address that M6 warned about.

**Out:** this is the door most often left open. In July 2026, the AI security company Pillar Security published seven sandbox escapes in four AI coding tools: Cursor, OpenAI's Codex, Google's Gemini CLI and Google's Antigravity. None of them broke the sandbox. In each case the agent, inside the sandbox, wrote a file that something outside the sandbox later trusted: a configuration file or a hook that the tool loaded and ran with full powers, or a shared Docker socket. The sandbox did its job. A trusted program then ran what came out of it.

Part M met the same lesson twice: model files saved with Python's `pickle` format run code when loaded ([M1](https://github.com/rajumandala/ai-supplychain/blob/main/notes/M1.%20Downloaded%20Models.md)), and inference servers that unpickled network messages let anyone run code (ShadowMQ, in M6). Data that crosses a boundary must not turn into code on the other side. For the screening sandbox:

1. **The only output is the result,** capped and treated as untrusted text, as in note 9.
2. **Everything else is thrown away with the sandbox.** Files written inside are never copied out, and nothing outside reads the scratch area.
3. **Nothing outside runs, loads or imports anything the sandbox produced.** If a later step ever needs a file from it, that file gets the same review as a file from a stranger.

## Step 5: limits, and a fresh start every time

- **Limits on everything.** CPU, memory, number of processes (a **fork bomb**, code that copies itself until the machine runs out of processes, stops at 64), scratch space and wall-clock time. These protect the other clients' work on the same server.
- **A fresh sandbox for every run, destroyed afterwards.** If Mallory's screening request could leave a file behind, Ravi's request could find it. One run, one sandbox, no shared state.
- **Pinned images.** The runner image is pinned by its digest, a hash of its contents, so a changed image refuses to start.
- **Every run is recorded.** The code, the input size, the result and any limit it hit go into note 14a's traces. A sandbox that tried the network, hit its memory limit or timed out is a signal worth an alert: model-written screening code has no reason to do any of those.

| Risk | Control |
|---|---|
| A kernel or runtime bug lets code out of a container | gVisor or a microVM for code the model wrote |
| A setting removes the wall | Never `--privileged`, never the Docker socket, never root inside |
| Data leaves through DNS or a "sandbox mode" that still has a network | No network device; test from inside; a logging proxy if one service is needed |
| Secrets inside the sandbox | Data only: no environment, keys, host folders or metadata route |
| A trusted program runs what the sandbox wrote | Only the capped result comes out; everything else is destroyed |
| One client's run affects another | Limits on every resource, and a fresh sandbox per run |

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions.

### ASI05: Unexpected Code Execution (RCE)

- **Example:** The screening code runs in a plain container as root. Mallory's post makes the model write code that uses a runtime bug like Leaky Vessels to reach the host's files.
- **Issue:** Model-written code shares a kernel with the broker's servers, so one bug turns a sandbox into the host.
- **Fix:** gVisor or a microVM, a non-root user, no extra powers, and a patched runtime.

### LLM02: Sensitive Information Disclosure

- **Example:** A vendor's code sandbox in "no network" mode still answers DNS. The model's code sends Ravi's holdings out a few characters at a time inside lookup names.
- **Issue:** The wall held, but the data left anyway.
- **Fix:** No network device at all, a test from inside that a lookup never arrives, and that test kept as a permanent eval case.

### LLM10: Improper Output Handling

- **Example:** The agent writes a configuration file in its workspace, and a tool outside the sandbox loads it and runs a command from it.
- **Issue:** A trusted program ran what came out of the sandbox, so the sandbox did not matter.
- **Fix:** Only the capped result leaves. Everything else is destroyed, and nothing outside runs or loads anything the sandbox produced.

### LLM06: Unbounded Consumption

- **Example:** The model writes screening code with a loop that starts new processes forever.
- **Issue:** Without limits, one request slows every other client's work on the server.
- **Fix:** Limits on CPU, memory, processes, disk and time, and an alert when a run hits one.

## Problem and next step

**Problem:** the assistant now has many entry points: the investor's message, uploads, web pages, vendor tools, news, memory, handoffs and model-written code. Each control was tested alone, against the attack that note was about. Nobody has attacked the whole system.

**Solution, in [10. Prompt Injection and Red Teaming](10.%20Prompt%20Injection%20and%20Red%20Teaming.md):** attack the assistant end to end, the way Mallory would, and turn every attack that works into a permanent test.
