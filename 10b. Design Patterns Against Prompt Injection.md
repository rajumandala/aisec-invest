The last note ended with guardrails that are soft: a classifier or a judge can be worded around. Every hard control in the course was something else, a rule in code. But each of those rules was invented for one attack, and the next feature will need a new one.

## The idea

Look back at the hard controls from notes 6 to 9a:

- Note 6: forward only the arguments we reviewed.
- Note 7: a request that reads news places no order.
- Note 8: a request that reads news cannot change memory.
- Note 8a: a summary that covers a news read carries the same flag.
- Note 9: the agent that reads news has no order tools, and hands off typed fields only.
- Note 9a: a request with an upload places no order.

None of them tries to spot the injection. Each one makes sure that **text from an attacker cannot reach a power**, whatever the text says. Researchers have named this move and the few shapes it takes. With the names, a team can review a new feature without waiting for the attack that shows what it needs.

This note covers three ideas:

1. **The lethal trifecta** and **the Agents Rule of Two**, for finding where an agent is exposed.
2. **Six design patterns**, for removing the exposure.
3. **Labels on every value** (the idea behind CaMeL), for replacing the one-off flags from notes 7 to 9a with one rule.

## Step 1: find the dangerous combinations

In June 2025 Simon Willison named the **lethal trifecta**. An agent can be made to steal data when it has all three of:

1. **Access to private data**, such as Ravi's holdings.
2. **Exposure to untrusted content**, such as a forum post or a vendor's tool description.
3. **A way to send data out**, such as a tool call to someone else's server, a link, or an image URL.

Any two are survivable. With all three, an injection in the content can read the data and send it out. Prompt injection will sometimes work, so the only reliable fix is to remove one leg.

In October 2025 Meta published the **Agents Rule of Two**, which widens the third leg. Within one session, an agent should have at most two of: **(A)** processing untrusted input, **(B)** access to sensitive systems or private data, and **(C)** changing state or communicating externally. Placing an order counts under (C), so the rule covers unwanted actions as well as data theft. If a task truly needs all three, a person supervises it.

The assistant through the course, checked against the three legs:

| Agent, from note | Untrusted input | Private data | Sends out or acts | Result |
|---|---|---|---|---|
| Assistant with vendor version 2 (6) | The vendor's description | Holdings | Tool arguments to the vendor | All three: Ravi's portfolio sent 20 times out of 20 |
| One agent that reads news and proposes orders (7) | Forum posts | Holdings | Orders | All three, made safe only by an `if` |
| Research agent whose reply is rendered as Markdown (10a) | Forum posts | Holdings in context | An image URL Ravi's phone fetches | All three: holdings sent to Mallory with no click |
| Order agent (9) | No | Holdings | Orders | Two |
| Research agent (9) | Forum posts | No | A reply to Ravi | Two |
| Logged-out browser agent (9a) | Web pages | No | Every page it opens is a request | Two, only while it holds no private data |

Two lessons from the table:

- **"Sending data out" hides in places nobody calls communication**: a tool argument, a search query, a link, an image, a URL the browser agent opens, an A2A task. For each one, ask whether a value from the context can end up in it.
- **The last row is safe only because of what is missing.** The day someone gives the browser agent Ravi's holdings "for context", every page it opens can carry them out. The legs must be checked every time a tool or a data source is added.

## Step 2: six patterns

In June 2025 a group of researchers from industry and universities published six design patterns for agents that resist prompt injection. All of them follow one principle: **once an agent has read untrusted input, that input must not be able to trigger an action that matters.**

| Pattern | How it works | Where the course used it |
|---|---|---|
| **Action-selector** | The model only picks one of a fixed set of actions and never reads what the action returns | Notes 1 and 2: the model turns a message into an `Order`, and code checks it |
| **Plan-then-execute** | The model fixes the plan before it reads untrusted data. The data can change values inside the plan, but not which actions run | Note 9: orders only for stocks the investor named |
| **LLM map-reduce** | Each untrusted document is read by its own isolated call that returns a closed type. Code combines the results | Not yet; Step 3 uses it |
| **Dual LLM** | A privileged model plans and calls tools but never sees untrusted text. A quarantined model reads that text but has no tools | Note 9: research and order agents, typed handoffs |
| **Code-then-execute** | The privileged model writes a small program, and an interpreter runs it and tracks where every value came from | Step 3, in a simple form |
| **Context-minimisation** | Remove untrusted text, or the parts of the prompt that no longer matter, before the next step | Note 8a: the context rebuilt on every call |

Each pattern buys safety with usefulness. An action-selector cannot answer "why is Infosys falling?". In the dual-LLM pattern, the privileged model cannot read the news it is meant to act on. The patterns protect **actions and data**. They do not make a reply built from poisoned text true. That stays the soft row in note 14.

## Step 3: from one flag to labels on every value

Note 7's `read_news` flag is the simplest version of an idea called **taint tracking**. It has two weaknesses that grew with every note:

- **It is too coarse.** Once any news is read, nothing can happen, so "why is Infosys falling? if it's bad news, sell all my Infosys" can never work.
- **Every new source needs a new flag.** Memory (note 8), summaries (note 8a) and uploads (note 9a) each needed their own rule. Someone has to remember the next one.

**CaMeL**, from Google DeepMind and ETH Zurich (March 2025), tracks this per value instead of per request. A privileged model writes the plan from the investor's words only. A quarantined model reads the untrusted text and returns plain values. An interpreter in code attaches a label to every value saying where it came from, and checks a policy before each tool runs.

A simple form for the assistant:

```python
@dataclass(frozen=True)
class Value:
    data: object
    sources: frozenset[str]        # "investor", "broker", "news", "upload", "memory_summary", ...

TRUSTED = frozenset({"investor", "broker"})

def is_trusted(v: Value) -> bool:
    return v.sources <= TRUSTED    # a value with no label counts as untrusted
```

The privileged model sees only Ravi's message, and returns a plan in a fixed shape: research INFY, then sell all of it if the news is negative. Code runs the plan:

```python
stock = Value("INFY", frozenset({"investor"}))                  # Ravi named it; matched in the instrument master
held = Value(get_holding(client_name)["INFY"]["quantity"], frozenset({"broker"}))

for doc in search_news("Infosys"):                               # map: one isolated call per document
    s = quarantined_sentiment(doc["text"])                       # no tools; returns Literal["negative", "neutral", "positive"]
    sentiments.append(Value(s, frozenset({"news"})))
sentiment = combine(sentiments)                                  # reduce, in code; the label is kept

if sentiment.data == "negative":
    propose(order_fields={"stock": stock, "quantity": held}, decided_by=[sentiment])
```

The policy runs in code before anything reaches `check_order` or the confirmation:

```python
def order_policy(order_fields: dict[str, Value], decided_by: list[Value]) -> list[str]:
    problems = [f"{name} came from {sorted(v.sources)}"
                for name, v in order_fields.items() if not is_trusted(v)]
    if any(not is_trusted(v) for v in decided_by):
        needs_source_in_confirmation()   # "Suggested because news looked negative (sources: ...)"
    return problems
```

What this gives:

- **Mallory cannot choose the order.** The stock comes from Ravi's words and the quantity from the broker. A ZENTECH order has no trusted source for its stock, so the policy rejects it. The quarantined model returns one of three words, so there is nowhere to put "buy 2000 ZENTECH".
- **The sell request works again**, which note 7's flag could not allow.
- **New sources are covered by default.** An A2A artifact (note 13) or a new tool result arrives without the `investor` or `broker` label, so it is untrusted until someone decides otherwise.

What it does not give, said plainly:

- **Mallory can still flip the condition.** A post written to look negative can make the sell happen. Ravi asked for that behaviour, but the attacker now decides *whether* it happens. That is why a decision based on untrusted data shows its sources in the confirmation, and still needs his exact "yes" (note 4).
- **Labels must follow control flow.** Anything decided inside the `if` depends on the news, even though no news text was copied into it. A tracker that only follows copied values misses this.
- **It is still research.** CaMeL is a prototype with its own interpreter, and agent frameworks do not offer this today. Most teams will run the coarse version from notes 7 to 9a, plus typed handoffs, and add labels where a real feature needs them.

## Step 4: a review question for every feature

Before a new tool, data source or agent goes in:

1. Which of the three legs does each agent now have? If any agent has all three, remove one.
2. Which pattern removes it, and what does it cost the feature?
3. Where can a value from untrusted text end up: an order field, a tool argument, a URL, a memory write?
4. After the fix, what can the attacker still change? Write it down as an accepted risk, or as a confirmation that shows the source.

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions.

### LLM01: Prompt Injection, and ASI01: Agent Goal Hijack

- **Example:** "why is Infosys falling? if it's bad news, sell all my Infosys", while Mallory's post asks for a ZENTECH buy.
- **Issue:** Note 7's flag stops the attack only by refusing Ravi's real request, and each new source needs its own flag.
- **Fix:** A plan from Ravi's words, untrusted text read only by a quarantined model that returns a closed type, and a policy that rejects any order field without a trusted source.

### LLM02: Sensitive Information Disclosure

- **Example:** The research agent's reply carries holdings in an image URL (note 10a), and the version 2 vendor received holdings in a tool argument (note 6).
- **Issue:** Both were the lethal trifecta. The way out was a channel nobody had listed as communication.
- **Fix:** List every outbound channel for each agent, and keep private data and untrusted content out of the same agent when one exists.

### LLM03: Excessive Agency

- **Example:** Someone gives the logged-out browser agent Ravi's holdings "for context".
- **Issue:** The agent now has all three legs, and every page it opens is a way out.
- **Fix:** The Rule of Two, checked whenever a tool or data source is added.

## Problem and next step

**Problem:** every control so far is hand-written: our own loop, our own dispatch, our own confirmation, our own guardrails and our own labels. Real teams build assistants on agent frameworks, which bring their own loop, tool handling and defaults. Do our controls survive the move, and what does the framework do that we did not ask for?

**Solution, in [11. Frameworks](11.%20Frameworks.md):** rebuild the assistant on an agent framework and find where each control now lives.
