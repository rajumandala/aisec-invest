The last note ended with a confirmation that has to wait. Ravi may reply minutes later from his phone, so the run must pause, be saved, and resume, and saved state is new data that someone can read or change.

## The idea

**LangChain** is a library of building blocks for model apps: model clients, tools, retrievers and prompts. **LangGraph**, from the same team, builds agents as a **graph**: each step is a node, edges decide what runs next, and a shared **state** object moves through the graph.

Two LangGraph features matter here:

- A **checkpointer** saves the state after every step, keyed by a `thread_id`. A run can stop and continue later, even on another server.
- `interrupt()` pauses the graph inside a node and waits for a human. The app later resumes the same thread with the human's answer.

That is the confirmation screen from note 4, built into the framework. It also creates a store of saved sessions holding prompts, holdings, proposed orders and confirmations. In AppSec terms, a checkpoint is a **server-side session** with a lot of sensitive data in it.

The code here has not been run, and LangGraph's details change between versions, so check them against the version you install.

## Step 1: the order flow as a graph

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command

class State(TypedDict):
    client_name: str
    prompt: str
    orders: list[dict]
    approved: list[dict]

def propose(state: State):                       # the model call: tools, loop, structured output
    result = call_model(instructions, state["prompt"], state["client_name"])
    orders = [o for o in (result.orders if result else []) if not check_order(o, state["client_name"])]
    return {"orders": [o.model_dump() for o in orders]}

def confirm(state: State):                       # pause for the investor; no model call in this node
    approved = []
    for order in state["orders"]:
        answer = interrupt({"question": f"Place {order['buy_or_sell'].upper()} {order['quantity']} {order['stock']} "
                                        f"at ₹{order['price']:,.2f} {order['order_type']}?"})
        if answer == "yes":
            approved.append(order)
    return {"approved": approved}

def place(state: State):                         # check again, then place exactly what was approved
    for data in state["approved"]:
        order = Order(**data)
        if not check_order(order, state["client_name"]):
            place_order(order, state["client_name"])
    return {}

graph = StateGraph(State)
graph.add_node("propose", propose)
graph.add_node("confirm", confirm)
graph.add_node("place", place)
graph.add_edge(START, "propose")
graph.add_edge("propose", "confirm")
graph.add_edge("confirm", "place")
graph.add_edge("place", END)
app = graph.compile(checkpointer=checkpointer)
```

The app starts a run, gets the pause with the question, shows it to Ravi, and later resumes:

```python
config = {"configurable": {"thread_id": thread_id}}
app.invoke({"client_name": session.client_name, "prompt": prompt}, config)   # pauses at confirm
app.invoke(Command(resume="yes"), config)                                     # later: Ravi said yes
```

## Step 2: what can go wrong with pausing and saving

**A resumed node runs again from the top.** When a graph resumes, the node that called `interrupt()` starts over, and the code before the interrupt runs a second time. If the model call and the interrupt were in the same node, the model would run again **after** Ravi said yes, and could produce a different order from the one he approved. This is note 4's rule ("the same object the investor saw, with no model call in between") broken by a framework detail. That is why `propose` and `confirm` are separate nodes, and `confirm` only reads the orders from the saved state.

**The thread ID is a session ID.** Whoever sends a `thread_id` resumes that thread. If the app takes it from the request, Mallory can resume Ravi's paused thread and answer "yes" to his order, or read his saved state. This is note 3's IDOR again, with a new key. The app must check that the thread belongs to the signed-in client, or derive the key from the session itself, for example `f"{session.client_name}:{random_id}"` with an ownership check on every resume.

**The identity in the state is data.** `client_name` lives in the saved state. Set it only from the session when the thread starts, and check it against the session on every resume. Never let a node take it from the model.

**Saved state is sensitive data at rest.** Checkpoints hold prompts, holdings, orders and every approval. The in-memory checkpointer is for experiments only. A real one writes to a database, and that database needs:

- Access limited to the app, never shared with analytics or support tools by default.
- Encryption at rest. LangGraph can encrypt checkpoints with its own serializer, which is a stronger guarantee than only encrypting the disk.
- A retention period: delete threads after the order is done or expires, and do not keep chat history forever because the default does.

**Stale approvals.** Ravi may approve an hour later, when the price has moved 8%. `place` runs `check_order` again, so the price band check uses the live price at the time of placing, not the time of proposing. An approval should also expire: a pause older than a few minutes asks again.

| Risk | Control |
|---|---|
| The model re-runs after approval | Model call and `interrupt()` in separate nodes |
| Mallory resumes Ravi's thread | Thread owned by the session; checked on every resume |
| Identity changed in saved state | Set from the session at the start; checked on resume |
| Saved sessions read by someone else | Restricted database, encrypted checkpoints, retention period |
| An old approval places a stale order | `check_order` runs again at `place`; approvals expire |
