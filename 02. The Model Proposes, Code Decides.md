The last note ended with orders that looked valid but were wrong: an invented market order, a zero quantity and a lost amount. A broker never sends a client-typed order without checking it, and the assistant's orders should be no different.

## The idea

> **The model proposes. Code decides.**

- The model's order is a **proposal**, like an order typed by a client. It can be useful, but it is not trusted.
- **Plain code checks it** against fixed rules before anything goes out. This code is reviewed and tested, and it gives the same answer every time. It does the job a broker's RMS (risk management system) does.
- **If any rule fails, the order is rejected.** Code never fixes an order by guessing. Guessing is the mistake the model made.

Why not just write "never use market orders" in the instructions? **An instruction only asks. Code enforces.** The model follows instructions most of the time, and an RMS that works most of the time is not an RMS.

## The change

Trusted data that the model cannot change, and a check that runs on every order:

```python
INSTRUMENTS = {"RELIANCE", "INFY", "TCS", "HDFCBANK"}   # instrument master
MAX_ORDER_VALUE = 500000                                # fat-finger limit: ₹5 lakh

def check_order(order: Order) -> list[str]:
    problems = []
    if order.stock not in INSTRUMENTS:
        problems.append(f"{order.stock} is not in the instrument master")
    if order.quantity <= 0:
        problems.append("quantity must be more than 0")
    if order.order_type != "limit":
        problems.append("the assistant may only create limit orders")
    if order.price <= 0:
        problems.append("price must be more than 0")
    if order.quantity * order.price > MAX_ORDER_VALUE:
        problems.append(f"order value is above the limit of ₹{MAX_ORDER_VALUE:,}")
    return problems   # empty list = accepted
```

Each rule records its own reason, so a rejection says exactly what is wrong. The instructions also ask the model to write the NSE symbol (RELIANCE, not Reliance).

## What happened

| Investor typed | Order from the model | Decision |
|---|---|---|
| buy 10 Reliance at 2900 limit | RELIANCE, 10, limit, 2900 | Accepted |
| buy Reliance worth 50000 | RELIANCE, 0, market, 0 | Rejected: quantity 0, market order, price 0 |
| sell all my Infosys | INFY, 0, market, 0 | Rejected: quantity 0, market order, price 0 |
| buy 1000 TCS at 3100 limit | TCS, 1000, limit, 3100 | Rejected: ₹31 lakh is above the ₹5 lakh limit |

Three things are worth noticing:

- **The invented values from the last note are now caught.** The market order and the zeros never get through.
- **The fat-finger order was read perfectly.** The model did its job. Only code knows the broker's limit, so only code can stop it.
- **Before the symbol instruction was added, the model wrote "Reliance" in one run and "RELIANCE" in another.** The check rejected the inconsistent one. The instruction makes the model usually right, and the code makes sure it does not matter when it is not.

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions.

### LLM10: Improper Output Handling

- **Example:** "buy 1000 TCS at 3100 limit" was read perfectly: 1000 TCS at ₹3,100, a ₹31 lakh order. The investor most likely meant 100.
- **Issue:** A correct reading of a dangerous order is still dangerous. The model does not know the broker's limits, so it cannot stop this.
- **Fix:** `check_order` rejects it: "order value is above the limit of ₹500,000". It rejects and never repairs, so code never guesses what the investor meant.

### LLM03: Excessive Agency

- **Example:** In the last note, "buy Reliance worth 50000" produced a market order. The only thing that could have stopped it was an instruction such as "never use market orders".
- **Issue:** An instruction only asks. The model still has the power to propose any order type and any size.
- **Fix:** The limit-only rule and the ₹5 lakh cap live in code. The same request now gets "Rejected: quantity 0, market order, price 0".

## Problem and next step

**Problem:** "buy Reliance worth 50000" and "sell all my Infosys" are perfectly reasonable requests, but the assistant can only reject them. To turn ₹50,000 into a quantity, it needs today's price. To sell "all", it needs to know how many shares this investor holds. Code can only check facts it has, and neither the model nor the code knows these.

**Solution, in [03. Tool Calling](03.%20Tool%20Calling.md):** give the assistant tools that fetch the live price and the investor's holdings from trusted systems.
