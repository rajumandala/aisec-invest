The last note ended with a list of monitoring signals and a kill switch. Both need data the team does not have yet. Nobody can see inside one request: which steps ran, what each one cost, why an order was rejected. And the model, the prompts and the vendors keep changing.

## The idea

**Observability** means being able to answer a new question about what the system did, from data it already records. **LLMOps** is the day-to-day work of running an AI system: watching it, paying for it, and changing it without breaking it.

An agent needs three kinds of data:

| Data | What it answers | Example |
|---|---|---|
| **Traces** | What happened in this one request, step by step? | Ravi's request: 3 model calls, 2 tool calls, `check_order` rejected the second order |
| **Metrics** | How is the whole system doing? | Cost per request, delay, rejection rate, guardrail hits per hour |
| **Logs** | What exactly was said or done at one point? | The tool error text, the alert from the injection classifier |

Traces are for engineers, kept for a short time. They are not the evidence record a regulator asks for, which has stricter rules and its own store.

This note shows the design. The code here has not been run, so no results are shown.

## Step 1: trace one request

A **trace** is a tree of **spans**, one span per step, each with a start time, an end time and some attributes. OpenTelemetry is the common standard, and it has conventions for AI calls (`gen_ai.*` attributes) that are still being finalised.

```python
tracer = trace.get_tracer("order-assistant")

def handle(prompt: str, client_name: str):
    with tracer.start_as_current_span("request") as root:
        root.set_attribute("client", pseudonym(client_name))          # never the raw client ID
        for step in range(MAX_STEPS):
            with tracer.start_as_current_span("model_call") as span:
                response = call_model(...)
                span.set_attribute("gen_ai.request.model", MODEL)
                span.set_attribute("gen_ai.usage.input_tokens", response.usage.input_tokens)
                span.set_attribute("gen_ai.usage.output_tokens", response.usage.output_tokens)
            for call in tool_calls(response):
                with tracer.start_as_current_span("tool:" + call.name):
                    run_tool(call)
        with tracer.start_as_current_span("check_order") as span:
            problems = check_order(order, client_name)
            span.set_attribute("problems", problems)
```

Now "why was my order rejected?" has an answer in seconds: open the trace, find the `check_order` span, read the problem.

**Traces are sensitive data.** Note 11 found that a framework sends traces, with prompts and holdings, to the provider's dashboard by default. The rules for our own traces:

- **Record structure and numbers by default**: step names, timings, token counts, tool names, check results. Leave out prompts, tool outputs and replies unless a debugging switch is turned on for a short time.
- **Pseudonymise the client.** A stable pseudonym lets engineers follow one investor's requests without seeing who it is.
- **Access control and a short retention period**, and the tracing service listed as a data processor.

## Step 2: cost and delay

Every request costs tokens, and an agent can use many per request. Track, per request and per investor:

- **Tokens and cost**, split into model calls, embeddings and judges.
- **Delay**, split by step, so the slow one is visible.
- **Steps per request.** A rise means the agent is going round in circles.

Ways to bring cost down, and the security question each one raises:

| Technique | Saving | Watch out for |
|---|---|---|
| **Prompt caching**: keep the stable prefix (instructions, tool definitions) the same on every call | Cheaper, faster input | Keep per-investor data after the stable part, never inside it |
| **A smaller model for easy steps**, such as summaries | Big savings | Never route a step that decides what code does to a weaker model without running the evals on it |
| **Capped context and tool results** (note 8a) | Fewer tokens per step | Say in the reply when a list was cut |
| **Budgets per investor** (note 10) | A hard ceiling on spend | An alert when one investor hits it often |

**Reasoning models** need two extra rules:

- **Their thinking costs money even when you do not see it.** A reasoning model writes hidden reasoning tokens before it answers, and they are billed as output. One hard request can use many times the tokens of its visible answer, so budgets and step metrics count reasoning tokens too.
- **The reasoning is not the reason.** Providers return a summary of the reasoning, or nothing. Research from 2025 found that models often leave out of their written reasoning a hint that changed their answer. So a reasoning summary is useful for debugging, but it is not evidence of why the assistant did something. The evidence is the trace: what the model read, what it returned and what code decided. A reasoning summary is also model text that may quote holdings or Mallory's post, so it follows the same rules as prompts: off by default in traces, never in the audit log as fact.

## Step 3: change without breaking

Things that change behaviour, and how to control each one:

- **The model.** Pin an exact model snapshot, not an alias that the provider moves to a new version. Providers retire models, so plan the upgrade before the date.
- **The prompts.** Instructions live in version control with a version number, and every trace records which version ran.
- **Vendors and frameworks.** Pinned tool fingerprints (note 6), pinned agent cards (note 13), pinned library versions.

A model or prompt change goes out in stages:

1. **Offline:** the eval suite from note 5, with every security case at 5 out of 5.
2. **Shadow:** the new version runs on a copy of real requests. Its orders are checked and recorded, never placed. Compare it with the current version.
3. **Canary:** a small share of investors get the new version. Watch the metrics: rejection rate, guardrail hits, steps per request, cost, complaints.
4. **Full rollout,** with the old version ready to switch back to.

**Feedback becomes tests.** When an investor marks a reply as wrong, it goes to a review queue. If it shows a real failure, it becomes an eval case, with personal data removed, so the same failure cannot come back.

Feedback is untrusted input too, because Mallory can send it. Two hundred "this answer was wrong" votes on replies where the assistant refused to place an order after reading news can make a team think the rule is hurting users, and weaken it. Her feedback can also carry text she wants to see later as an expected output. So:

- **A person reviews every case before it enters the evals.** Votes only sort the review queue. They never change a test or a rule by themselves.
- **Feedback never changes a security case.** A complaint about a refusal can lead to a reviewed change of policy (note 5), never to an edited test.
- **Count feedback per account.** Many votes from a few accounts, or from new accounts, are a signal to look at, not a trend.
- **If feedback is ever used to fine-tune a model,** it becomes training data, and Mallory's votes become data poisoning (LLM05). [Part M](https://github.com/rajumandala/ai-supplychain) covers that.

## Step 4: when something goes wrong

A short runbook, written before it is needed:

1. **Contain:** the kill switch from note 14 turns the assistant off; the normal trading screens keep working.
2. **Find the scope:** search traces for every request with the same pattern, such as orders after a news read, or one prompt version.
3. **Find the cause:** the trace shows the step; the version attributes show what changed.
4. **Fix and add a test:** the failure becomes a security case before the assistant is turned back on.

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions. The code in this note has not been run, so each example shows what would happen.

### LLM02: Sensitive Information Disclosure

- **Example:** Traces record every prompt and tool output, so Ravi's holdings sit in the tracing service, readable by every engineer.
- **Issue:** Debugging data becomes a second, unlisted copy of client data.
- **Fix:** Structure and numbers by default, a pseudonym for the client, content only behind a short-lived debugging switch, access control and short retention.

### LLM06: Unbounded Consumption

- **Example:** A prompt change makes the agent loop until `MAX_STEPS` on most requests. Nobody notices for a week.
- **Issue:** Cost doubles quietly, and delay rises for everyone.
- **Fix:** Metrics for steps, tokens and cost per request, with alerts when they jump.

### LLM04: Supply Chain

- **Example:** The code names a model alias, and the provider moves it to a new version overnight.
- **Issue:** Behaviour changes with no change in our code and no eval run.
- **Fix:** Pin the exact snapshot, record it in every trace, and upgrade through evals, shadow and canary.

### ASI10: Rogue Agents

- **Example:** After a prompt change, the share of rejected orders triples. Each rejection looks normal on its own.
- **Issue:** A drift in behaviour is invisible one request at a time.
- **Fix:** Metrics compared before and after every change, a canary rollout, and a switch back to the old version.
