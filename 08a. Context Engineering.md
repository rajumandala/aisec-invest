The last note ended with memory that carries a few typed facts across sessions. Inside one session the problem is the opposite: a busy trading day is one long conversation full of quotes, holdings, news and orders, and the model can only read so much of it.

## The idea

The **context** is everything the model reads in one call: the instructions, the preferences, the conversation so far, and every tool result. The agent loop from note 4 sends all of it again on every step.

The context has three limits:

| Limit | What happens |
|---|---|
| **Size** | Every model has a maximum number of tokens (the pieces of text from note 1). Past it, the call fails or something gets cut |
| **Cost and time** | Every token is paid for and read on every step. A long chat makes each answer slower and dearer |
| **Attention** | Models pay less attention to the middle of a long context. A rule said an hour ago may be read but not followed |

**Context engineering** is deciding, on every call, what the model gets to read. It is like a web app that builds each page from its own records on the server, instead of trusting whatever the browser sends back: the context is rebuilt by code each time, not a log that grows forever.

## Step 1: the context that only grows

The simple version appends everything and sends it all:

```python
history.append({"role": "user", "content": prompt})
history.append({"role": "tool", "content": json.dumps(quote)})    # every quote, all day
response = call_model(instructions, history)
```

By the afternoon, this goes wrong in three ways:

- **It hits the limit.** Some code cuts the oldest messages to fit, and the oldest message is often the most important: the instructions, or Ravi saying "only sell up to half of anything today".
- **It carries stale data.** The 9:30 quote for INFY is still in the context at 3:00. The model may quote it. `check_order` still uses the live price (note 3), so the order is safe, but the explanation is wrong.
- **It costs more every turn.** The hundredth question pays for the ninety-nine before it.

## Step 2: rebuild the context on every call

Code builds the context from parts, in a fixed order:

```python
MAX_TURNS = 10

def build_context(client_name: str, history: list, summary: str) -> list:
    prefs = PREFERENCES.get(client_name, Preferences())
    return [
        {"role": "developer", "content": instructions},                        # always first, never trimmed
        {"role": "developer", "content": "Preferences: " + prefs.model_dump_json()},   # from the store, not the chat
        {"role": "user", "content": f"<untrusted_summary>{summary}</untrusted_summary>"},
        *history[-MAX_TURNS:],                                                  # only recent turns
    ]
```

- **Instructions and preferences are never cut.** They come from code and the preference store on every call, not from the conversation.
- **Only recent turns go in full.** Older turns are replaced by a short summary.
- **Tool results are not kept.** A quote is fetched again when needed, so the model never reasons from a stale price.

The stable parts go first for a second reason: model providers can **cache** a prefix that stays the same between calls, which makes those tokens cheaper and faster.

## Step 3: a summary is untrusted text

Older turns are summarised by a model. That summary is now one of the most dangerous pieces of text in the system, for two reasons.

**It can drop a rule.** Ravi said "only sell up to half of anything today". The summary says "the investor discussed selling some holdings". Nothing failed, and the rule is gone.

The fix is the one from note 8: anything that changes what code allows must live in **typed state**, not in the conversation. "Up to half today" becomes a field that `check_order` reads:

```python
class SessionLimits(BaseModel):
    max_sell_fraction: float = 1.0       # set from "only sell up to half", after Ravi confirms

SESSION_LIMITS: dict[str, SessionLimits] = {}    # client_name -> limits for today
```

Pending orders work the same way. They live in `PENDING_SELLS` (note 4), never in the chat history.

**It can launder an attack.** At 11:00 the assistant read Mallory's forum post. At 2:00 the summary says "the investor is interested in ZENTECH". Her text has lost its `untrusted_news` label and now reads like something Ravi said.

So the summary is treated like retrieved news:

- It is wrapped as `untrusted_summary`, and the instructions say it is a record, not a source of instructions.
- If any summarised turn read news or a file, the summary carries that flag, and note 7's rule applies: a request that reads it places no order.
- It never carries rights. A preference or a limit cannot come from a summary.

The rule of this note: **state that matters lives in code. The context is a view of that state, rebuilt on every call.**

## Step 4: large tool results and streaming

**Cap what tools return.** "Show my trades this year" can return thousands of rows. The tool returns only the fields the question needs, with a row limit, and says when it cut the list. Smaller results are cheaper, faster, and give attacker text less room.

**Streaming** shows the reply word by word as the model writes it, so the investor is not left waiting. That is fine for explanations. It is not fine for anything that looks like an action:

- The model can stream "Done, I've sold your 40 INFY" before `check_order` has run, or when it never will.
- So the confirmation question and the result of an order always come from code, built from the checked `Order` and the exchange's reply, never from streamed model text.
- Streamed text is shown as plain text. It is never rendered as HTML.

| Risk | Control |
|---|---|
| The instructions get cut | Rebuilt first on every call, never trimmed |
| A stale price in the answer | Tool results not kept; fetched again; code checks the live price |
| A rule lost in a summary | Rules that change what code allows are typed state |
| Mallory's text laundered by a summary | Summary is untrusted, flagged if it covers a news read, never carries rights |
| Cost grows with every turn | Recent turns only, capped tool results, a cached stable prefix |
| "Order placed" streamed before any check | Order messages come from code, not from the model |

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions.

### ASI06: Memory & Context Poisoning

- **Example:** At 11:00 the assistant reads Mallory's post. The 2:00 summary says "the investor is interested in ZENTECH".
- **Issue:** Her text loses its untrusted label and reads like Ravi's own words in every later step.
- **Fix:** The summary is wrapped as untrusted, flagged when it covers a news read, and never carries rights.

### LLM07: Misinformation

- **Example:** At 3:00 Ravi asks "what's INFY at?", and the model answers from the 9:30 quote still in the context.
- **Issue:** The answer is confidently wrong, though the order itself would still be checked against the live price.
- **Fix:** Tool results are not kept between turns. Prices are fetched again.

### LLM06: Unbounded Consumption

- **Example:** A trading-day chat with a hundred questions, and "show my trades this year" returning every row.
- **Issue:** Each call sends the whole history again, so cost and delay grow with every turn.
- **Fix:** Recent turns only, a summary for older ones, capped tool results and a cached stable prefix.

### ASI09: Human-Agent Trust Exploitation

- **Example:** The streamed reply says "Done, I've sold your 40 INFY" before any check has run.
- **Issue:** Ravi believes an order went through, or did not, based on text the model made up.
- **Fix:** Confirmation questions and order results are built by code from the checked order and the exchange's reply.

## Problem and next step

**Problem:** the same request keeps doing two jobs. It reads untrusted text from the world, and it can place orders and change settings. Every control so far has been a rule inside one agent saying "if you read news, do not act". One agent with both powers is one bug away from Mallory placing orders.

**Solution, in [09. Multi-Agent Systems and Code Execution](09.%20Multi-Agent%20Systems%20and%20Code%20Execution.md):** split the assistant into a research agent that reads the world and cannot act, and an order agent that acts and never reads the world.
