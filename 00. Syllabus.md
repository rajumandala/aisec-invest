## How the notes are built

Every note follows the same pattern:

1. **It starts from the previous problem.** The opening line restates the problem the last note ended on.
2. **It adds one idea to the same assistant.** The code changes as little as possible from the previous note.
3. **It shows the security point with a real run.** That means a real request or a real attack, not only theory.
4. **It names the OWASP risks.** A short table lists each OWASP risk the note meets, the issue it causes in the assistant, and the fix.
5. **It ends on the next problem.** The last section names what the assistant still cannot do safely, and links to the note that solves it.

| 3 | Tool calling | Looks up live quotes and the investor's holdings | Holdings come from the logged-in account, never from an account ID the model supplies. Mallory cannot see Ravi's holdings. Prices and quantities copied by the model are checked again by code | LLM01, LLM02, LLM03, ASI02, ASI03 | "Book profit on all my gainers" needs several steps, and one call cannot do that | Done |
| 4 | The agent loop | Works through several steps and places an order only after the investor confirms it | A step limit stops runaway loops. Confirmation is tied to the exact order, so any change needs a new confirmation. A confirmation is not a safety check: pending sells are blocked so shares cannot be sold twice | LLM06, LLM03, ASI08, ASI09 | Answers change from run to run. | 5 | Evaluations | A fixed set of tests that runs before every change | Security checks become repeatable tests, like a security gate in a build pipeline. Security cases must pass every run. | 6 | MCP | Gets quotes from a third-party market-data server | Another company's tool descriptions and results are untrusted, and the server can change its tools later. Pin the reviewed tools and refuse to start if they change. What reaches the model is what the server publishes, not what its documentation says. With several servers, one server's description can shadow another's tools: pin every server, name tools after their server, route by a reviewed table, and pass only closed values | LLM02, LLM04, ASI02, ASI04 | The broker also runs its own MCP server, and developers connect servers nobody reviewed | Done |
| 6a | MCP servers in production | Publishes the broker's own MCP server, so investors can use their own AI apps with their account | The server is a public API: OAuth tokens issued for it and checked on every call, the client taken from the token, small scopes that expire, typed arguments and no shell, only the fields a task needs, and every call logged. Developers' MCP servers come from an approved list | MCP07, MCP01, MCP02, MCP05, MCP10, MCP09 | The assistant knows nothing about today's news or announcements | Note written, not run |
| 7 | RAG (retrieval) | Answers "why is this stock falling?" from announcements, results and news | Mallory's pump-and-dump post contains hidden instructions. Retrieved text is data, never instructions. "The model resisted" is not a control: a request that reads news places no order. A poisoned post can still crowd out the real announcement | LLM01, LLM05, LLM09, LLM07, ASI01, ASI06 | The news is public. The broker's own documents are not, and the index does not know who may read what | Done |
| 7a | Permission-aware retrieval | Searches the broker's own documents: premium research, each client's contract notes, internal memos | Mallory asks a normal question and gets a premium report, a staff memo or Ravi's contract note: IDOR through search, with no injection. Each document carries its principals; the search filters on the reader's principals from the session before ranking; results are checked against the source. Permissions sync, deletions reach embeddings and caches, and anything made from a document inherits its strictest permission. In shared spaces such as a support ticket, search with the permissions of whoever will read the answer, not whoever started the assistant | LLM02, LLM09, ASI03, LLM01 | Every session starts empty. The investor has to repeat their preferences | Note written, not run |
| 8 | Memory | Remembers defaults such as delivery or intraday, "no F&O" and stocks to avoid | Mallory's post gets saved as "this investor prefers intraday F&O". Each investor's memory must stay separate and protected | ASI06, LLM03, LLM02, LLM09 | A trading day is one long conversation. The context fills up, and old prices and rules sit next to new ones | Note written, not run |
| 8a | Context engineering | Handles a full trading day in one chat: recent turns, a summary of older ones, fresh prices | Instructions and preferences are rebuilt first on every call, never trimmed. Rules that change what code allows are typed state, not chat. A summary is untrusted and can launder an attack. "Order placed" text comes from code, never from streamed model output | ASI06, LLM07, LLM06, ASI09 | One agent that reads untrusted posts and can also place orders has too much power | Note written, not run |
| 9 | Multi-agent systems and code execution | A research agent and an order agent with separate powers; model-written screening code runs in a sandbox | The research agent cannot place orders. A handoff between agents is untrusted input. Model-written code is untrusted code. Model-written SQL is SQL injection with the model as the typist: a typed tool first, otherwise a read-only copy of only this client's rows | ASI05, ASI07, ASI03, LLM03, LLM10 | Investors send screenshots and PDFs, and some agents browse the web. Instructions hide where people cannot see them | Note written, not run |
| 9a | Multimodal and browser agents | Reads screenshots, PDFs and voice notes; browses exchange sites for announcements | Ravi is trusted for his intent, not for the content of a file he forwards. A request with an upload places no order. Browsing is read-only, logged out and allowlisted. A browser agent never clicks "Buy": orders go through the API. A spoken yes is not confirmation | LLM01, ASI01, ASI03, LLM02, ASI09 | The assistant now has many entry points. It must be attacked as a whole | Note written, not run |
| 10 | Prompt injection and red teaming | A full attack exercise on the assistant | Each successful attack becomes a new test in the evaluation set. A jailbreak attacks the model's safety training; a prompt injection attacks our app. Roles and the instruction hierarchy make injection rarer but are not a boundary. Invisible Unicode is removed in code before text reaches the model, and look-alike links fail an exact allowlist. Many-turn and many-shot attacks beat checks that read one message, so soft checks read the conversation. Also: nothing in the instructions or tool descriptions should be secret, and per-investor rate limits and cost budgets stop one user running up the bill | LLM01, ASI01, ASI09, LLM08, LLM06 | Some harm is in the reply, not an order: a PAN, a leaking link, an invented price, a stock tip | Note written, not run |
| 10a | Guardrails | Filters on text going into and out of the model | Rules in code are hard; classifiers and model judges are soft. No images and only allowlisted links in replies, so rendering cannot leak holdings. PAN patterns removed before replies are shown or logged. Prices in a reply checked against tool results. Guardrails are tested for misses and false alarms | LLM10, LLM02, LLM01, LLM07 | Guardrails are soft, and each hard rule so far was invented for one attack | Note written, not run |
| 10b | Design patterns against prompt injection | A review method for every new tool, source or agent, and labels on every value instead of one flag per source | Find the lethal trifecta (private data, untrusted content, a way out) and keep each agent to two of three. Six patterns: action-selector, plan-then-execute, map-reduce, dual LLM, code-then-execute, context-minimisation. Values carry their source, so an order field from news is rejected. The attacker can still flip a condition, so its source is shown in the confirmation | LLM01, ASI01, LLM02, LLM03 | Everything so far is hand-written. Do the controls survive a framework? | Note written, not run |
| 11 | Frameworks | The same assistant rebuilt with an agent framework | Find where each control now lives, and what the framework does by default. Prompts and skills loaded at runtime are dependencies too: pinned, reviewed, never writable by the agent | LLM04, ASI04, LLM02, ASI07 | Graph frameworks add saved state and pause points | Note written, not run |
| 11a | LangChain and LangGraph | Order confirmation as a pause point; saved sessions | Saved sessions hold holdings and order history. Who can read them? | ASI03, LLM02, ASI08 | Outside agents need part of the investor's data and powers. A shared login gives them everything | Note written, not run |
| 12 | Agent identity and delegated authorisation | Lets an outside tax agent read trades with the investor's consent; the assistant itself runs with a per-investor token | Two identities in every request: the user (`sub`) and the agent (`act`). Scoped, short-lived, revocable tokens instead of passwords. No shared service account, so a prompt cannot pick whose account is used. Tokens never enter the model's context. A scope is not a confirmation | ASI03, LLM03, LLM02, ASI09 | Every control so far assumes the investor is there to read and confirm. Some agents run while nobody is watching | Note written, not run |
| 12a | Agents without a human present | A morning watcher that reads announcements for the investor's holdings and can sell within a standing instruction | The approval moves to setup time: a typed mandate, created in the app and never in chat, with limits and an expiry. The plan is fixed at setup; the model returns a closed label and code builds the order. Only listed sources can start a run, and run caps stop an attacker getting many tries. A short-lived token per run, revoked with the mandate. Every action is notified, and a circuit breaker and kill switch replace the person watching | LLM03, ASI03, LLM06, ASI10 | The assistant needs help from another company's agent it has never worked with | Note written, not run |
| 13 | Agent to Agent (A2A) | Asks an outside tax agent for tax-saving sales, and accepts proposals from an adviser's agent | The Agent Card is a claim: allowlist, signature and pin it. Send the minimum data and never forward the investor's token. The remote agent's answer is untrusted: typed fields only, checked against holdings, shown as suggestions, never placed as orders | ASI07, ASI04, LLM02, ASI03, ASI08 | Controls are spread over files, frameworks, stores and other companies' agents. The whole system needs a review | Note written, not run |
| 14 | Architecture review | A threat model of the assistant | Data flow, trust boundaries (including outside agents), and which control covers which risk. The model provider is a third party: storage off and context kept in our code, the minimum sent, hosted tools reviewed as vendors, a scoped key with a spending limit. Also: monitoring that spots an agent acting outside its job, such as orders after news reads or unusual tool calls | All; ASI08, LLM02, ASI10 | Monitoring needs data nobody collects yet, and the model, prompts and vendors keep changing | Note written, not run |
| 14a | Observability and LLMOps | Traces of every request, cost and behaviour metrics, staged rollouts | Traces hold client data: record structure and numbers by default, pseudonymise clients. Pin exact model snapshots, not aliases. Every change goes through evals, shadow and canary, with a way back. Feedback becomes eval cases only after review, because feedback is untrusted input too | LLM02, LLM06, LLM04, ASI10 | Secure does not mean allowed. Brokers and algorithmic orders are regulated | Note written, not run |
| 15 | Governance | SEBI rules, accountability, logs and evidence | Who is accountable for an order or an answer that the AI produced Also: audit logs of every model call, tool call and order, kept as evidence. | ASI09, ASI10 | End of the course | Note written, not run |
