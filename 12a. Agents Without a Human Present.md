The last note ended with tokens that let an agent act for Ravi with a small set of powers. Every control so far also assumed something else: that Ravi is there, in the chat, reading the reply and saying "yes". Many agents run when nobody is watching.

## The idea

An **unattended agent** runs without a person in the conversation. It starts in one of two ways:

- **On a schedule**, such as every morning at 9:00.
- **On an event**, such as a new announcement, an email or a webhook.

Ravi sets one up: "each morning, read the announcements for my holdings. If one of them cuts its guidance, sell half of it."

Three things change, and each one removes a control the course relied on:

| What changes | The control it removes |
|---|---|
| **The approval comes before the action**, days earlier | The exact "yes" for the exact order (note 4) |
| **Nobody reads the output** when it is produced | Ravi noticing a strange reply or a strange order |
| **The trigger is input**, and an event can be started by someone else | Ravi choosing when the agent runs |

In note 10b's terms, the agent has all three legs: untrusted input (announcements), private data (holdings) and the power to act (orders). The Rule of Two says such an agent needs a person supervising it, and here there is none. So one leg has to go, or be shrunk until the worst case is small.

## Step 1: the simple version

The quickest way to build it is to run the whole assistant from note 9 as a scheduled job:

```python
def every_morning():
    for client_name in WATCHERS:
        token = LONG_LIVED_TOKENS[client_name]            # saved when the watcher was set up
        run_agent(watch_instructions, "check today's announcements for my holdings",
                  tools=[search_news, get_holding, get_quote, place_order], token=token)
```

Everything the course built is undone in a few lines:

- **No confirmation.** `place_order` is a tool, because nobody is there to say yes.
- **A long-lived token with order powers**, stored for months, for every investor who set up a watcher.
- **The model reads the news and decides the order.** Mallory's post at 3:00 a.m. is read at 9:00 by an agent that can sell, and nobody sees it until the contract note arrives.
- **The attacker gets retries.** An injection that works one time in a hundred is a weak attack when Ravi is watching. Against an agent that runs every day for every watcher, it works somewhere every day.

## Step 2: the approval becomes a mandate

When the "yes" cannot come at action time, it has to come at setup time. It has to be specific enough that code can enforce it later. India's UPI AutoPay works this way: the person approves a maximum amount, a frequency and an end date once, and the bank refuses any debit outside it.

The mandate is typed state, like the preferences in note 8:

```python
class Mandate(BaseModel):
    id: str
    client_name: str                          # from the session when Ravi set it up
    action: Literal["sell"]                   # the only action the agent may take alone
    stocks: list[str]                         # only these, checked against the instrument master
    trigger: Literal["guidance_cut", "loss_reported"]
    max_fraction: float = 0.5                 # at most half of the holding
    max_value_per_day: int = 100000           # ₹1 lakh across all runs in a day
    max_runs_per_day: int = 3
    expires: datetime                         # 30 days at most
```

The rules for creating one:

- **Created in the broker's app, never in chat.** A mandate loosens what can happen without a "yes", so note 8's rule applies: chat can tighten a risk setting, never loosen it. A forum post that asks the assistant to "set up a watcher" has no way to create one.
- **Shown in full and confirmed**, with an exact "yes", like an order: "Sell up to half of INFY or TCS if either announces a guidance cut. At most ₹1,00,000 a day. Ends 18 November."
- **It expires**, and Ravi can see and cancel it in Settings.

## Step 3: the plan was made at setup

The mandate is also the plan. In note 10b's terms this is **plan-then-execute**, with the plan made days before any untrusted text is read. At run time the model does not choose an order. It answers one closed question about each announcement:

```python
def on_announcement(doc: dict, m: Mandate):
    if doc["source"] != "nse_announcements" or doc["symbol"] not in m.stocks:
        return                                                    # a forum post cannot start a run
    if runs_today(m) >= m.max_runs_per_day:
        return pause(m, "too many runs today")
    label = quarantined_classify(doc["text"], Literal["guidance_cut", "loss_reported", "other"])   # no tools
    if label != m.trigger:
        return
    held = get_holding(m.client_name)[doc["symbol"]]["quantity"]   # from the broker
    order = Order(stock=doc["symbol"], buy_or_sell="sell", quantity=int(held * m.max_fraction),
                  order_type="limit", price=live_price(doc["symbol"]))   # built by code, never by the model
    problems = check_order(order, m.client_name) + mandate_problems(order, m)
    audit("mandate_run", mandate=m.id, doc=doc["id"], label=label, order=order.model_dump(), problems=problems)
    if problems:
        return notify(m.client_name, f"Your standing instruction {m.id} did not act: {problems}")
    place_order(order, m.client_name, token=mint_token(m))
    notify(m.client_name, f"Sold {order.quantity} {order.stock} under standing instruction {m.id}, "
                          f"because of {doc['source']} {doc['id']}. Cancel the instruction in Settings.")
```

What each line does:

- **Who can start a run is decided by code.** Only the exchange feed can trigger it, only for stocks in the mandate, and only a few times a day. Mallory's forum posts never start anything.
- **The model's whole output is one of three words.** The stock comes from the announcement's own metadata and must be in the mandate. The quantity comes from the holdings and the mandate, and the price from the feed.
- **`check_order` and `mandate_problems` still run.** `mandate_problems` checks the action, the stock, the fraction, the daily value and the expiry, so a bug in the code above it is still bounded.
- **Ravi is told after the fact**, every time, with the source. Nobody reads the output when it is produced, so the agent sends it to the person it acted for.

What an attacker can still do, said plainly: a misleading announcement, or one the model misreads, can trigger the sell. The worst case is the mandate: half of one named stock, at most ₹1 lakh that day, with a notification. Note 10b called this flipping the condition. A mandate is how its size is decided in advance.

## Step 4: a token for nobody signed in

At 9:00 Ravi is not signed in, so there is no session to take `client_name` from. The tempting fix is the long-lived token from Step 1. Instead, using note 12's tokens:

- **The scheduler holds a grant, not a token.** When the mandate is created, the broker records a grant tied to that mandate. The scheduler keeps it in a secrets vault, never in the agent's context.
- **Each run gets a fresh token** with `sub: ravi`, `act: watch-agent`, a scope that allows only this mandate's action, and a few minutes of life.
- **Cancelling the mandate revokes the grant.** The next run cannot get a token.

```python
def mint_token(m: Mandate) -> str:
    grant = VAULT.get(f"mandate:{m.id}")                  # revoked when the mandate is cancelled or expires
    return exchange_token(grant, sub=m.client_name, act="watch-agent",
                          scope=f"orders:mandate:{m.id}", ttl_seconds=300)
```

The broker's API then checks the order against the mandate as well, so even a stolen run token can do no more than the mandate allows.

## Step 5: monitoring is the human now

With nobody in the loop, monitoring stops being a second line and becomes the main way anyone notices a problem:

- **A circuit breaker per mandate.** More runs than usual, a rejected order, or an alert from the injection classifier pauses the mandate and tells Ravi. A paused mandate resumes only when he confirms in the app.
- **A global kill switch** for all unattended agents, separate from the one for the chat assistant in note 14. These agents fail differently, and stopping them should not stop Ravi from trading.
- **A model change is a change to every mandate.** Ravi approved the mandate while one model version was classifying announcements. A new version can classify the same text differently. Unattended flows get their own eval cases, such as a misleading announcement and a real guidance cut, and go through shadow and canary first (note 14a).
- **State from earlier runs is untrusted.** If the agent keeps notes between runs ("INFY already flagged yesterday"), those notes were written by a model that read announcements. Treat them like the summaries in note 8a.

The safest default is still a person. An unattended agent that **proposes and notifies** ("INFY cut its guidance. Proposed: sell 20 INFY. Tap to confirm, expires in 30 minutes") keeps note 4's confirmation. The mandate that acts alone is for the narrow cases where Ravi chose speed over that, and its limits show exactly how much he gave up.

| Risk | Control |
|---|---|
| An order with no confirmation | A mandate: typed, confirmed in the app, limited and expiring |
| A post or a chat message creates a mandate | Mandates only in the broker's app; chat cannot loosen risk settings |
| The model chooses the order | Plan fixed at setup; the model returns a closed label; code builds the order |
| Anyone can start a run | Triggers only from listed sources and stocks, a cap on runs per day |
| Many runs give an injection many tries | Run caps, a circuit breaker, a value cap per day |
| A long-lived token with order powers | A grant in a vault, a short-lived token per run, revoked with the mandate |
| Nobody sees what happened | A notification for every action and every refusal, with the source |
| A model update changes every mandate | Eval cases for unattended flows, shadow and canary |

## Step 6: when the agent pays

Ravi's watcher sells shares inside the broker, where `check_order` and the mandate live in the same company's code. Many agents now spend money elsewhere: they book travel, pay bills or buy from online shops. The merchant and the bank are other companies. They never saw Ravi say yes, and they cannot read the broker's mandate table.

In 2025 the payments industry started building the mandate from Step 2 into the payment itself:

- **AP2, the Agent Payments Protocol**, was published by Google in September 2025 with more than 60 payments and technology companies, as an extension to A2A (note 13) and MCP (note 6). It uses three signed records it calls **mandates**. The **Intent Mandate** records what the person allowed: what to buy, a price limit and a time window. The **Cart Mandate** records the exact cart the merchant offered and the person, or the agent within the intent's limits, accepted. The **Payment Mandate** tells the card network that an agent was involved. Each is a **verifiable credential**: a record signed with a key, so anyone can check who signed it and that nobody changed it.
- **The Agentic Commerce Protocol**, published by OpenAI and Stripe the same month, gives the agent a **shared payment token** instead of a card number. Stripe scopes the token to one merchant and the cart total, so it cannot be spent anywhere else or for more.

Both carry this course's rules to companies that do not share the broker's code:

1. **The limit lives in the credential, not in the prompt.** A scoped token or a signed intent with a price limit is enforced by the merchant and the payment network, whatever the agent was told. This is note 12's scoped token and Step 2's mandate, checked by someone else.
2. **The agent never holds the card.** It holds a token that only works for this purchase, like the per-run token in Step 4.
3. **The signing key belongs to the person's device, never to the model.** If the agent could sign its own Intent Mandate, a forum post could write one. The mandate is created and signed in the person's app, as in Step 2.
4. **A signature proves what was approved, not that it was wise.** An injected agent can still buy the wrong thing inside the limits: a listing Mallory planted, at the maximum price. Keep the limits small, allowlist merchants where possible, and notify the person of every purchase, as in Step 5.
5. **The records are the evidence.** When Ravi says "I never asked for that", the signed intent and cart show what he approved and what the agent chose. That is note 15's accountability question, answered with signatures instead of chat logs.

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions.

### LLM03: Excessive Agency

- **Example:** The morning job gives the agent `place_order` because nobody is there to confirm.
- **Issue:** The model reads announcements and forum posts and decides orders on its own, with the investor asleep.
- **Fix:** A mandate decided by Ravi in the app. The model returns only a closed label, and code builds the order within the mandate's limits.

### ASI03: Identity and Privilege Abuse

- **Example:** Every watcher stores a long-lived token with order powers, so the scheduler can act "as Ravi" at 9:00.
- **Issue:** A leak of the scheduler's store gives orders on every watcher's account, for months.
- **Fix:** A grant per mandate in a vault, a five-minute token per run with `act: watch-agent`, and revocation when the mandate ends.

### LLM06: Unbounded Consumption

- **Example:** Mallory's posts, or a flood of announcements, start a run each.
- **Issue:** Every run costs model calls, and every run is another try for an injection.
- **Fix:** Only listed sources and stocks can start a run, with a cap on runs per day and a circuit breaker.

### ASI10: Rogue Agents

- **Example:** After a model update, the classifier labels routine announcements as guidance cuts, and mandates start selling.
- **Issue:** Nobody is in the conversation to notice.
- **Fix:** A notification for every action, a circuit breaker per mandate, a kill switch for unattended agents, and eval cases plus a canary for these flows before any model change.

## Problem and next step

**Problem:** every agent so far is the broker's own, or, like ExampleTax, was registered in advance and connected by Ravi. Now the assistant itself needs help from an outside agent, run by another company, that it has never worked with. How does it find that agent, talk to it, and decide what to trust in its answers?

**Solution, in [13. Agent to Agent (A2A)](13.%20Agent%20to%20Agent%20%28A2A%29.md):** a standard protocol for agents to discover each other and hand over tasks, and the controls that keep another company's agent at arm's length.
