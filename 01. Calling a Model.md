The order assistant starts here. An investor types an order in plain English, and the assistant has to turn it into an order the broker's system can use.

A few words first, because every note uses them. A **model**, or **LLM** (large language model), is a program trained on a huge amount of text. Given some text, it writes the text most likely to come next, which is enough for it to answer questions, follow instructions and fill in forms. Companies such as OpenAI, Anthropic and Google run models and let other programs use them over the internet. The text sent to a model is the **prompt**, and everything the model reads in one call is its **context**. Models read and write text in small pieces called **tokens**, roughly three-quarters of a word each, and providers charge per token.

The code in these notes is Python. The text around each piece of code says what it does, so you can follow every idea without reading the code. Market and security terms are explained where they first appear, and all of them are collected in [A4. Glossary](A4.%20Glossary.md).

## A plain call

A model call is a web request. Your code sends text and gets text back. The provider's **API** (application programming interface) is the set of web requests it accepts, and an **API key** is the secret that proves the request comes from a paying customer.

```python
response = client.responses.create(
    model="gpt-6.1-sol",
    instructions="You are an order assistant for an Indian broker that reads the investor's message and states the order: stock, buy or sell, quantity, order type and price.",
    input="buy 10 Reliance at 2900 limit",
)
print(response.output_text)
```

| Part | Written by | Trusted? |
|---|---|---|
| `instructions` | The developer | Yes |
| `input` | The investor | No. It is like an order typed by a client |
| The answer | The model | No. It is the model's reading of the order |

The table holds only if the call runs on the broker's server. A tempting shortcut for a mobile app is to call the model API straight from the phone. Then:

- **The API key ships inside the app.** Anyone can pull it out of the app package or read it from the network traffic, then spend the broker's budget or read anything stored under that key (note 14).
- **The instructions ship inside the app too.** A user can change them, so the "Yes" in the first row becomes "written by whoever runs the app".
- **Every check in this course would run on a device the user controls.** The order checks, the identity rules and the confirmation from later notes could all be skipped.

So the app sends only the investor's message and their login session. The server holds the key, builds the instructions, calls the model and runs every check. A payment app keeps its bank API key off the phone for the same reason.

The answer reads well ("Quantity: 10 shares, Price: ₹2,900 per share"), but it is a paragraph. Code would have to pull "10" out of "10 shares", and the wording can change on every run.

For "buy Reliance worth 50000", the plain answer said the quantity was "to be calculated" and the order type was "not specified", and it asked a question back. Free text lets the model say "I don't know".

## Structured output

Structured output gives the model a fixed shape, called a schema. The answer must match it, the same way a response must match an API contract.

```python
class Order(BaseModel):
    stock: str
    buy_or_sell: Literal["buy", "sell"]
    quantity: int
    order_type: Literal["market", "limit"]
    price: float

response = client.responses.parse(
    model="gpt-6.1-sol", instructions=instructions, input=prompt, text_format=Order
)
order = response.output_parsed   # an Order object, or None if the model refused
```

`Literal` limits a field to exact values, so "Purchase" or "BUY" cannot come back. If the model refuses, `output_parsed` is `None`, so check for it before using the order.

## What happened

| Investor typed | Order from the model |
|---|---|
| buy 10 Reliance at 2900 limit | quantity 10, limit, price 2900.0 |
| buy Reliance worth 50000 | quantity 0, **market**, price 0.0 |
| sell all my Infosys | quantity 0, **market**, price 0.0 |

The first order is correct. The other two show the problem:

- **A required field forces an answer.** In free text the model said "not specified". The schema gave it no way to say that, so it filled in placeholders.
- **"Market" was invented.** The investor never said market. A **market order** executes at whatever the price is. A **limit order**, which the first message asked for, executes only at the stated price or better.
- **The ₹50,000 disappeared.** `Order` has no field for an amount, so the investor's limit was silently dropped.
- **Zero passes the schema.** `0` is a valid `int`. On another run the model may write a realistic number like 17, and nothing would show it is a guess.

> **Valid structure is not correct content.** The schema guarantees the shape of the order. It does not guarantee the order is what the investor meant.

The model has no live data either. It does not know today's Reliance price or how many Infosys shares this investor holds, so it cannot work out these numbers even if it tries.

## OWASP risks in this note

OWASP, the open security community behind the classic web Top 10, publishes lists of the top risks in AI apps. The notes on MCP also use the [OWASP MCP Top 10](A3.%20OWASP%20MCP%20Top%2010.md).

### LLM10: Improper Output Handling

- **Example:** For "buy Reliance worth 50000", the model returned `quantity 0`, `order_type "market"`, `price 0.0`. The schema accepted it, because 0 is a valid `int` and "market" is an allowed value.
- **Issue:** The app would use this order as it came back. Model output going straight into a trade is the same mistake as a user's typing going straight into a database query, which web developers know as SQL injection (note 9).
- **Fix:** Not yet. The next note checks every order in code before it goes anywhere.

### LLM07: Misinformation

- **Example:** For "sell all my Infosys", the model again returned quantity 0, a market order and price 0.0. The investor never said "market", and the model knew neither the holdings nor the price.
- **Issue:** The model filled in values it did not know, and nothing in the order shows they are guesses. On another run it may write a realistic number like 17, which looks like a real answer.
- **Fix:** Not yet. [03. Tool Calling](03.%20Tool%20Calling.md) gives the assistant the live price and the holdings, so the numbers come from data.

## Problem and next step

**Problem:** the assistant produces orders that look valid but can be wrong: an invented order type, a zero quantity, a lost amount. If these went straight to the exchange, a wrong order would become a real trade. A broker never sends a client-typed order without checking it first.

**Solution, in [02. The Model Proposes, Code Decides](02.%20The%20Model%20Proposes%2C%20Code%20Decides.md):** treat the model's order as a proposal. Code checks it against fixed rules, the way a broker's risk management system (RMS) checks every order, before anything goes out.
