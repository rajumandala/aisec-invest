The order assistant starts here. An investor types an order in plain English, and the assistant has to turn it into an order the broker's system can use.

## A plain call

A model call is a web request. Your code sends text and gets text back.

```python
response = client.responses.create(
    model="gpt-6.1-sol",
    instructions="You are an order assistant for an Indian broker that reads the investor's message and states the order: stock, buy or sell, quantity, order type and price.",
    input="buy 10 Reliance at 2900 limit",
)
print(response.output_text)
```

| Part | Written by | Trusted? |
|---|---|---|
| `instructions` | The developer | Yes |
| `input` | The investor | No. It is like an order typed by a client |
| The answer | The model | No. It is the model's reading of the order |

The answer reads well ("Quantity: 10 shares, Price: ₹2,900 per share"), but it is a paragraph. Code would have to pull "10" out of "10 shares", and the wording can change on every run.

For "buy Reliance worth 50000", the plain answer said the quantity was "to be calculated" and the order type was "not specified", and it asked a question back. Free text lets the model say "I don't know".

## Structured output

Structured output gives the model a fixed shape, called a schema. The answer must match it, the same way a response must match an API contract.

```python
class Order(BaseModel):
    stock: str
    buy_or_sell: Literal["buy", "sell"]
    quantity: int
    order_type: Literal["market", "limit"]
    price: float

response = client.responses.parse(
    model="gpt-6.1-sol", instructions=instructions, input=prompt, text_format=Order
)
order = response.output_parsed   # an Order object, or None if the model refused
```

`Literal` limits a field to exact values, so "Purchase" or "BUY" cannot come back. If the model refuses, `output_parsed` is `None`, so check for it before using the order.

## What happened

| Investor typed | Order from the model |
|---|---|
| buy 10 Reliance at 2900 limit | quantity 10, limit, price 2900.0 |
| buy Reliance worth 50000 | quantity 0, **market**, price 0.0 |
| sell all my Infosys | quantity 0, **market**, price 0.0 |

The first order is correct. The other two show the problem:

- **A required field forces an answer.** In free text the model said "not specified". The schema gave it no way to say that, so it filled in placeholders.
- **"Market" was invented.** The investor never said market. A market order executes at whatever the price is.
- **The ₹50,000 disappeared.** `Order` has no field for an amount, so the investor's limit was silently dropped.
- **Zero passes the schema.** `0` is a valid `int`. On another run the model may write a realistic number like 17, and nothing would show it is a guess.

> **Valid structure is not correct content.** The schema guarantees the shape of the order. It does not guarantee the order is what the investor meant.

The model has no live data either. It does not know today's Reliance price or how many Infosys shares this investor holds, so it cannot work out these numbers even if it tries.

## Problem and next step

**Problem:** the assistant produces orders that look valid but can be wrong: an invented order type, a zero quantity, a lost amount. If these went straight to the exchange, a wrong order would become a real trade. A broker never sends a client-typed order without checking it first.

**Solution, in [02. The Model Proposes, Code Decides](02.%20The%20Model%20Proposes%2C%20Code%20Decides.md):** treat the model's order as a proposal. Code checks it against fixed rules, the way a broker's RMS checks every order, before anything goes out.
