The last note ended with controls that are all hand-written: our own loop, our own dispatch and our own confirmation. Real teams build on agent frameworks, which bring their own loop, tool handling and defaults.

## The idea

An **agent framework** provides the parts we wrote by hand in notes 3 to 9: tool definitions from plain functions, the agent loop, handoffs between agents, and tracing. It saves code. It also moves decisions out of our code and into the framework's **defaults**.

Moving to a framework is like moving an app onto a web framework. The checks you wrote by hand still need a home, and the framework's defaults become your security settings unless you change them.

This note uses the **OpenAI Agents SDK** (`openai-agents`), because the assistant already uses OpenAI models. The questions apply to any framework. Framework details change between versions, so check them against the version you install.

## Step 1: the same assistant, rebuilt

```python
from dataclasses import dataclass
from agents import Agent, Runner, RunConfig, RunContextWrapper, function_tool
from agents.exceptions import MaxTurnsExceeded

@dataclass
class Session:
    client_name: str                     # set by our code from the login, never by the model

@function_tool
def get_holding(ctx: RunContextWrapper[Session]) -> dict:
    """Get the signed-in client's holdings: for each NSE symbol, the quantity and average buy price."""
    return HOLDINGS.get(ctx.context.client_name, {})

@function_tool
def get_quote(stock: str) -> float | None:
    """Get the last traded price of an NSE stock."""
    return QUOTES.get(stock)

order_agent = Agent(name="Order assistant", instructions=instructions, model=MODEL,
                    tools=[get_quote, get_holding], output_type=Orders)

def call_model(prompt: str, client_name: str) -> Orders | None:
    try:
        result = Runner.run_sync(order_agent, prompt, context=Session(client_name),
                                 max_turns=MAX_STEPS,
                                 run_config=RunConfig(trace_include_sensitive_data=False))
    except MaxTurnsExceeded:
        return None                      # step limit reached: no guessing
    return result.final_output
```

Everything after `call_model` stays ours and unchanged: `check_order`, `confirm` and `place_order` run in our code on `result.final_output`.

## Step 2: where each control now lives

| Control | Hand-written version | With the framework |
|---|---|---|
| Identity from the session (note 3) | `get_holding(client_name)` passed by `dispatch` | The **run context**. It goes to tools but is not sent to the model. The tool takes no account argument |
| Strict tool schemas (note 3) | `"strict": True` | `function_tool` builds strict schemas from type hints by default |
| Step limit (note 4) | `MAX_STEPS` loop | `max_turns`. The default is higher than ours, so set it. Running out raises an exception: catch it and place nothing |
| RMS checks (note 2) | `check_order` after the model | Still ours, after the run. An **output guardrail** can also run it, as plain code |
| Confirmation (note 4) | `confirm(order)` | Still ours. Never a tool the model can call |
| Pinned vendor tools (note 6) | `check_vendor_tools()` at startup | Not built in. The framework's MCP client lists the vendor's tools and gives the model the vendor's descriptions. Keep our check, or wrap the vendor in our own reviewed tool |
| Separate agents (note 9) | Two calls with two tool lists | Two `Agent` objects. But see handoffs below |

## Step 3: defaults we did not ask for

**Tracing is on.** Every run is traced and, by default, sent to the model provider's tracing dashboard, along with the prompts, tool inputs and tool outputs. For us that means Ravi's holdings leave in a second place nobody listed in the data flow. `trace_include_sensitive_data=False` keeps the inputs and outputs out of the traces, and tracing can be turned off completely. Decide which, and write it down.

**Handoffs carry the conversation.** When one agent hands off to another, the next agent sees the conversation history by default, including what earlier agents read. A research agent that hands off to the order agent passes along Mallory's post with it, which is exactly what note 9 said not to do. Handoffs can filter the history, but the safe design is still the one from note 9: the order agent is never a handoff target from research.

**Tool errors go to the model.** By default, when a tool raises an exception, its error message is sent back to the model so it can try again. Exception text can contain internal details, such as file paths, SQL or another client's ID. Catch errors inside tools and return a plain message.

**Guardrails are not all equal.** The framework's input and output guardrails can call a model to judge the request. A model judging a model is useful, but it is still a soft defence. A guardrail that runs `check_order` as plain code is a control.

**The framework is a dependency.** It runs our tools, builds the prompts and handles the vendor's MCP tools, so a malicious or careless release changes the assistant. Pin its version in `uv.lock` and review upgrades like any other dependency.

**Instructions can be a dependency too.** Some setups load instructions while the agent runs instead of from our code: a prompt pulled from a prompt hub by name, a **skill** (a folder with an instruction file, and often scripts, that the agent loads when a task matches it), or a prompt that an MCP server publishes. Whatever is loaded lands in the context with the rank of our own instructions (note 10), and a skill's scripts run with the agent's permissions. It is note 6's rug pull aimed at the instructions themselves. Whoever can change the hub entry, the shared folder or the server changes the assistant's rules, with no code change and no eval run. Treat loaded instructions as code:

- Keep them in our repo, or pin an exact version, such as a commit hash, never "latest".
- Review a change to them like a change to `check_order`, and run the evals (note 5).
- Load skills only from a reviewed folder that the agent itself cannot write to. An agent that can save a new skill writes its own future instructions, which is note 8's poisoned memory with more power.
- Run a skill's scripts in the sandbox from note 9, never in the app process.
- Record the version of every loaded prompt and skill in the logs of each request, so a change in behaviour can be traced to a change in instructions.

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions.

### LLM04: Supply Chain

- **Example:** A new release of `openai-agents` changes how tools are called or how prompts are built. Or the assistant pulls its research instructions from a prompt hub as "latest", and someone edits the hub entry.
- **Issue:** The framework and the loaded instructions now shape the assistant, so a change to either changes it without a code change.
- **Fix:** Pin the framework in `uv.lock`, keep prompts in the repo or pinned by commit hash, load skills only from a reviewed folder the agent cannot write to, and review upgrades like any other dependency.

### ASI04: Agentic Supply Chain Vulnerabilities

- **Example:** The vendor's MCP server is plugged into the framework's own MCP support.
- **Issue:** The framework lists the vendor's tools and hands the model the vendor's descriptions. Version 2's poisoned description would reach the model again.
- **Fix:** Keep our `check_vendor_tools()` pin check, or wrap the vendor in our own reviewed tool.

### LLM02: Sensitive Information Disclosure

- **Example:** Ravi types "sell all my Infosys". By default the trace, including the `get_holding` output with his quantities and buy prices, goes to the model provider's tracing dashboard. A tool error message can also carry a file path or another client's ID back to the model.
- **Issue:** His data leaves in a place nobody listed in the data flow.
- **Fix:** `trace_include_sensitive_data=False`, or tracing off, and errors caught inside tools with a plain message returned.

### ASI07: Insecure Inter-Agent Communication

- **Example:** The research agent hands off to the order agent.
- **Issue:** By default the order agent sees the whole conversation, including Mallory's post.
- **Fix:** The order agent is never a handoff target from research.

## Problem and next step

**Problem:** every control so far assumes one broker and one assistant, with `client_name` taken from the investor's session. Investors also use outside agents, such as a tax-filing agent, that need part of their data. A shared password or an account-wide API key would give such an agent all of the investor's powers, and the broker could not tell the agent from the investor.

**Solution, in [12. Agent Identity and Delegated Authorisation](12.%20Agent%20Identity%20and%20Delegated%20Authorisation.md):** give each agent its own identity and a small, short-lived, revocable set of powers that the investor grants and code checks.

**Go deeper (optional, Part 2):** this framework runs the whole request in one go, but a real confirmation can take minutes. [11a. LangChain and LangGraph](deep-dives/11a.%20LangChain%20and%20LangGraph.md) builds the confirmation as a pause point that is saved and resumed, and secures the saved sessions.
