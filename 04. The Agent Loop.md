The last note ended with a request that one round of tool calls cannot handle: "book profit on all my gainers". The model cannot know which stocks to quote until it has seen the holdings, and none of its orders should go out without the investor's say.

## The idea

An **agent** is the same tool round trip from the last note, repeated:

1. Call the model.
2. If it asked for tools, run them, send the results back, and go to step 1.
3. If it answered, stop.

The model chooses each next step, so nobody knows in advance how many steps there will be. That is the power, and also the risk. A confused or manipulated model can keep calling tools for ever, and every round costs time and money. So the loop always has a **hard step limit in code**. When the steps run out, it stops and returns nothing. It does not guess.

## Step 1: the loop

Two small data changes come first. Holdings now include the average buy price, so that "gainer" means something: a stock now worth more than the investor paid for it. To **book profit** is to sell such a stock and take the gain.

The answer can be several orders, so the model returns a list:

The round trip from the last note goes inside a `for` loop:

```python
MAX_STEPS = 5      # the agent loop stops after this many rounds of tool calls

def call_model(instructions, prompt, client_name: str):

    for step in range(1, MAX_STEPS + 1):
        response = client.responses.parse(model=MODEL, instructions=instructions, input=messages, tools=tools, text_format=Orders)
        calls = [item for item in response.output if item.type == "function_call"]
        if not calls:

            print(f"  step {step}: {call.name}({call.arguments})")
```

## Step 2: confirmation tied to the exact order

An order that passes the checks is still only a proposal. Before anything goes to the exchange, the **investor** must agree to it. That is only useful if they agree to **the exact order that will be sent**. There are two ways to get this wrong:

- **Confirming the model's words instead of the order.** The model writes "I'll sell your 40 Infosys" while the order says 400. The investor said yes to a sentence, not to the order.
- **Letting anything change the order after the yes.** If "yes" goes back to the model as a new message, the model produces the orders again, and a new run can produce different numbers.

The rules:

- **Code builds the question from the order's fields**, never from text the model wrote.
- **On "yes", code places that same order.** The model plays no part between the yes and the placement.
- **Each order needs its own yes.** A changed order is a new order.
- **Only an exact "yes" counts.** "y", "ok" and "sure" place nothing.

It is the same idea as a bank's one-time password (OTP) that is tied to the amount and the payee: what you see is what you sign. The model also has no `place_order` tool at all. It can only propose.

```python
def confirm(order: Order) -> bool:
    # built from the order's fields only, never from text the model wrote
    question = f"Place {order.buy_or_sell.upper()} {order.quantity} {order.stock} at ₹{order.price:,.2f} {order.order_type}? (yes/no) "
    return input("  " + question).strip().lower() == "yes"

        problems = check_order(order, client_name)
        if problems:
            ...                                       # rejected: the investor is never asked
        elif confirm(order):
            place_order(order, client_name)           # the same object the investor saw
```

### A confirmation is not a safety check

The first test run placed **two** sell orders for 40 INFY, one for "book profit" and one for "sell all my Infosys". Ravi holds only 40. Each order passed `check_order` on its own, because the holdings still said 40, and Ravi said yes both times.

> **A confirmation shows that the investor agreed. It does not show that the order is safe.**

A broker's RMS handles this by **blocking** the quantity of a pending sell order. The shares stay in the holdings until **settlement**, when the exchange actually moves the shares and the money, usually the next working day. Until then they cannot be sold twice. The assistant now does the same:

```python
PENDING_SELLS = {}   # (client_name, stock) -> quantity already sold in this session

def place_order(order: Order, client_name: str):
    if order.buy_or_sell == "sell":
        key = (client_name, order.stock)
        PENDING_SELLS[key] = PENDING_SELLS.get(key, 0) + order.quantity
    print("  PLACED", order.model_dump_json())     # a real app calls the broker's order API here

# in check_order, for sells:

        if order.quantity > available:
            problems.append(f"{client_name} can sell only {available} {order.stock}")
```

## What happened

| Investor's answer | First order: sell 40 INFY | Second order: sell 40 INFY |
|---|---|---|
| yes | Placed | Rejected before any question: can sell only 0 INFY |
| y | Not placed: not an exact yes | Asked, and placed after yes, because nothing was blocked |

The model still proposed 40 the second time, because the holdings really are still 40. The tool reports the facts, and code decides what is allowed.

One honest point: the step limit was never reached in these runs. Every request finished in one or two rounds. It is a ceiling that ordinary requests do not touch. A later note on attacks shows why it is needed.

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions.

### LLM06: Unbounded Consumption

- **Example:** "book profit on all my gainers" took two rounds: `get_holding`, then `get_quote` for INFY and TCS. A confused or manipulated model could keep asking for tools round after round.
- **Issue:** Every round is a paid model call, and the model decides when to stop.
- **Fix:** `MAX_STEPS = 5`. When the steps run out, the loop returns nothing and places nothing. No run in this note came close to the limit.

### LLM03: Excessive Agency

- **Example:** The model proposed "sell 40 INFY at 1480".
- **Issue:** If the model had a `place_order` tool, that proposal would already be a trade, and nobody would have seen it first.
- **Fix:** The model has no `place_order` tool. Only code places an order, and only after the investor says yes.

### ASI09: Human-Agent Trust Exploitation

- **Example:** The model could write "I'll sell your 40 Infosys" while the order it returned says 400.
- **Issue:** Ravi would approve the sentence, not the order. Human approval is a control only if the human sees what will actually be sent.
- **Fix:** Code builds the question from the order's fields: "Place SELL 40 INFY at ₹1,480.00 limit? (yes/no)". Only an exact "yes" counts, and code places that same order. Answering "y" placed nothing.

### ASI08: Cascading Failures

- **Example:** Ravi ran "book profit on all my gainers" and then "sell all my Infosys". Both proposed selling 40 INFY. He holds only 40, but both orders passed `check_order` and he said yes twice, so 80 were sold.
- **Issue:** The first order did not change what the second check saw. One step's result did not reach the next step.
- **Fix:** Pending sells are blocked in code. The second order is now rejected before Ravi is asked: "ravi can sell only 0 INFY".

## Problem and next step

**Problem:** the same request does not always take the same path. "Sell all my Infosys" took two rounds in one run and one round in the next, with the same loop and the same words. Every result here was safe, but we only know that because we read each output by eye. When the instructions, the tools or the model change, nobody will re-read every case by hand, so a change that breaks a rule could go unnoticed.

**Solution, in [05. Evaluations](05.%20Evaluations.md):** a fixed set of test cases, including every attack so far, that runs automatically before any change goes in.
